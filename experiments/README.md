# `experiments/` — конфиги прогонов и их результаты

Здесь живут две вещи:

1. **Конфиги** `*.yaml` — по одному файлу на прогон. Коммитятся в git: это
   описание того, что именно запускалось.
2. **Папки результатов** `<name>/` — веса, логи, скоры, метрики. В git **не**
   попадают (они большие и легко воспроизводятся из конфига + кэша).

```text
experiments/
├── lfcc_statpool.yaml            # конфиг полного прогона (в git)
├── smoke_mini.yaml               # конфиг smoke-прогона на датасете `mini` (в git)
└── lfcc_statpool/                # результаты прогона (не в git)
    ├── metrics.jsonl
    ├── ckpt_epoch0003.pt
    ├── best.pt
    ├── final.pt
    ├── scores.parquet
    └── eval_metrics.json
```

Имя папки результатов = поле `name` в конфиге.

---

## Один конфиг на обучение и оценку

Стадии 2 и 3 читают **один и тот же файл**:

```bash
uv run python -m src.train    --config experiments/lfcc_statpool.yaml
uv run python -m src.evaluate --config experiments/lfcc_statpool.yaml
```

Это не экономия файлов, а гарантия: признак и архитектура у обучения и оценки
тогда заведомо одни и те же, и рассинхрон «оценили не тем, чем учили» невозможен
по построению. Стадия 2 читает `data.train`, `data.val`, `model`, `train`;
Стадия 3 — `data.test`, `eval`; секции друг друга они игнорируют.

Готовый пример со всеми полями и комментариями — `lfcc_statpool.yaml`.

## Разбор секций конфига

### `name`

Имя прогона. Определяет папку артефактов `experiments/<name>/`. Прогон с тем же
`name` **продолжит** предыдущий (см. «Возобновление» ниже) — для нового
эксперимента берите новое имя.

### `feature`

```yaml
feature:
  name: lfcc          # ключ реестра экстракторов — и всё
```

**Параметров здесь нет.** Одно имя признака = одна конфигурация = одна папка кэша
`data/features/<name>-<hash>/`. Раньше была секция `overrides`, и она создавала
разрыв: конфиг мог описать конфигурацию, которую CLI Стадии 1 построить не умел
(параметров он не принимал), то есть сослаться на папку, которую нечем наполнить.
С v15 старый конфиг с `overrides` падает с внятным сообщением, а не молча ищет
несуществующий кэш.

Нужна другая настройка признака — заводится **именованный экстрактор** (~6 строк в
`features.py`), после чего он одинаково доступен и Стадии 1, и конфигу:

```python
@register_extractor
@dataclass(frozen=True)
class LFCCNoDeltas(LFCC):
    name: ClassVar[str] = "lfcc_nodelta"
    with_deltas: bool = False
```

Заодно у каждой изученной конфигурации появляется имя, которое можно поставить в
строку таблицы результатов.

Список доступных признаков с параметрами: `uv run python -m src.data.features --list`.

> Асимметрия с `model.params` намеренная: у модели гиперпараметры не влияют на
> раскладку кэша на диске и целиком сохраняются в чекпойнте (`model_params`),
> поэтому рассинхрону там взяться неоткуда.

### `model`

```yaml
model:
  name: statpool_mlp
  params:
    hidden: 128
    dropout: 0.3
```

`params` попадают в чекпойнт, поэтому Стадия 3 восстанавливает модель нужного
размера, не заглядывая в YAML.

### `data`

```yaml
data:
  train:
    - {dataset_id: asvspoof2019_la, split: train}
  val:
    - {dataset_id: asvspoof2019_la, split: dev}
  test:
    - {dataset_id: asvspoof2019_la, split: test}
    - {dataset_id: for-2seconds,    split: test}
  t_fixed: 400
```

- **`train` / `val` / `test`** — списки селекторов `{dataset_id, split}`. При
  нескольких датасетах манифесты склеиваются. В `test` несколько датасетов —
  это нормальный режим: метрики считаются **по каждому отдельно**, и именно из
  сравнения строк читается кросс-датасетный вывод.
- **`t_fixed`** — общая длина входа в кадрах (400 ≈ 4 с при hop 10 мс). Стадия 3
  берёт `t_fixed` **из чекпойнта**, а не отсюда: менять его между обучением и
  оценкой означало бы оценивать модель на входе другой длины.
> **Объём прогона задаётся только этими списками.** Механизма подвыборок в
> проекте нет (удалён в v15): чтобы прогнать быстро, берут маленький датасет, а не
> срез большого. Для smoke есть `mini` (`python -m src.data.mini`, конфиг
> `smoke_mini.yaml`); для быстрого прогона на реальном домене — флаг Стадии 1
> `--limit N`, после которого Стадия 2 обучится ровно по посчитанному кэшу.

### `train` (Стадия 2)

```yaml
train:
  epochs: 5
  lr: 0.001
  weight_decay: 0.0
  pos_weight: auto     # auto | none | <число>
  ckpt_every: 1        # сохранять чекпойнт каждые N эпох
  keep_last: 3         # ротация: держать последние K чекпойнтов
```

`pos_weight: auto` считает `N_neg / N_pos` по фактически используемым train-меткам
(после отсева примеров, которых нет в кэше признаков) — коррекция дисбаланса
классов.

`keep_last` клампится к ≥ 1: без чекпойнта нет возобновления.

### `eval` (Стадия 3)

```yaml
eval:
  weights: best        # best | final | путь к .pt
  window: fixed        # 'full' / 'sliding' не реализованы
  bootstrap: 1000      # повторов бутстрэпа для CI; 0 — выключить
  bootstrap_seed: 1337
  ci: 0.95
  min_coverage: 0.99
  shard_rows: 20000
```

- **`window: fixed`** — окно `t_fixed` кадров с начала записи, ровно как на
  валидации Стадии 2. `full` и `sliding` намеренно не реализованы: это
  содержательные варианты метода, которые надо обосновывать и мерить, а не
  настройки инфраструктуры. Слот в конфиге оставлен, чтобы решение не было
  замуровано.
- **`min_coverage`** — минимальная доля тестовых примеров, которые нашлись в
  кэше признаков. Ниже — прогон падает: метрика считалась бы по неполному тесту,
  то есть с другим знаменателем. Обойти осознанно: `--allow-missing`, честно
  оговорив покрытие в работе.

### `runtime`

```yaml
runtime:
  device: cpu          # cpu | cuda
  batch_size: 16
  num_workers: 0
  seed: 1337
```

Переопределяет дефолты из `src/config.py`. Это единственное место, где живёт
знание о железе — переезд на GPU не требует правок кода.

`num_workers` на CPU подбирайте осторожно: загрузка данных и обучение
конкурируют за ядра, а каждый воркер дублирует память.

## Артефакты прогона

| Файл | Кто пишет | Что внутри |
|---|---|---|
| `metrics.jsonl` | Стадия 2 | по строке на эпоху: `epoch`, `train_loss`, `val_eer`, `val_threshold`, `lr` |
| `ckpt_epoch*.pt` | Стадия 2 | модель + оптимизатор + эпоха + метаданные; последние `keep_last` |
| `best.pt` | Стадия 2 | веса с минимальным val-EER |
| `final.pt` | Стадия 2 | веса последней эпохи |
| `scores.parquet` | Стадия 3 | `dataset_id, utt_id, split, label, attack_type, score` |
| `eval_metrics.json` | Стадия 3 | паспорт прогона + блок `per_dataset`: EER, порог, бутстрэп-CI, матрицы ошибок в двух точках, разбивка по атакам, покрытие |
| `scores_parts/` | Стадия 3 | временные шарды + `_state.json`; удаляются после успешной склейки |

**Стадия 3 по умолчанию грузит `best.pt`.** Оговорка: на малой или шумной
валидации «лучшая эпоха» может оказаться удачей, а не улучшением — на полном val
это не проблема, на smoke интерпретируйте осторожно.

### Что лежит в чекпойнте

Кроме весов и состояния оптимизатора — блок `meta`: `model_name`, `model_params`,
`feature`, `feature_hash`, `in_channels`, `t_fixed`. Благодаря этому чекпойнт
**самодостаточен**: Стадия 3 восстанавливает модель по нему, а не по YAML, — веса
и конфиг могут оказаться от разных прогонов.

### Что лежит в `eval_metrics.json`

Помимо метрик — паспорт прогона: какие веса, какая эпоха, метаданные чекпойнта,
окно, **конвенция скора** и покрытие кэша. Конвенция записана специально, чтобы
число нельзя было прочитать наоборот: в проекте больше ⇒ спуф, а в официальных
протоколах ASVspoof — наоборот.

Метрики — **по каждому датасету отдельно**. Общего EER по смеси нет намеренно:
он смешал бы разные домены и разные классовые пропорции в одно
неинтерпретируемое число.

## Возобновление и перезапуск

**Обучение.** Прерванный прогон, запущенный **той же командой**, подхватывает
последний чекпойнт (модель + оптимизатор + эпоха) и продолжает с невыполненной
эпохи. `metrics.jsonl` дописывается и дедуплицируется по эпохе.

**Оценка.** Скоры пишутся шардами; при рестарте уже посчитанные ключи
пропускаются. Рядом с шардами лежит `_state.json` — **отпечаток условий** прогона
(веса, эпоха, `feature_hash`, `t_fixed`, окно, селекторы).
Изменились условия — старые шарды удаляются с предупреждением, а не смешиваются
с новыми. Это штатный сценарий, а не ошибка: без отпечатка смена весов при живых
шардах молча склеила бы скоры двух разных прогонов в один файл.

> ⚠️ **Поэтому не переиспользуйте `name` для другого эксперимента.** Изменили
> модель или гиперпараметры и запустили под тем же именем — обучение попытается
> продолжить с чужого чекпойнта. Новый эксперимент = новое `name` (или удалите
> папку результатов).

## Рабочий цикл

1. Скопируйте `lfcc_statpool.yaml` под новым именем, поменяйте `name`.
2. Правьте признак / модель / гиперпараметры.
3. Проверьте, что цепочка жива, на `smoke_mini.yaml` (датасет `mini`, минуты):
   цикл, чекпойнты, лог и val-EER. Числа оттуда не интерпретируются.
4. Когда конфигурация устоялась — прогоните свой конфиг на полных датасетах.
5. Итоговые числа берите с полного теста: на малом тесте оценка EER имеет
   высокую дисперсию, а порог определён плохо. К итоговым числам прикладываются
   бутстрэп-доверительные интервалы.

## Типовые ошибки

| Сообщение | Что делать |
|---|---|
| `нет кэша признаков … (_spec.json отсутствует)` | прогнать Стадию 1 для этого признака |
| `C кэша (X) ≠ C признака <name> (Y)` | секция `feature` в YAML не соответствует папке кэша |
| `модель обучена на признаке с хэшем …, а в конфиге … даёт …` | приведите `feature` к конфигу обучения — иначе оценка шла бы на других признаках |
| `нет весов … — сначала Стадия 2` | прогнать обучение или указать `--weights final` / путь |
| `нет папки эксперимента …` | `name` не соответствует ни одному прогону |
| `в конфиге нет data.test` | добавить секцию тестовых селекторов |
| `eval.window='full' не реализован` | оставить `window: fixed` |
| `покрытие 0.97 < min_coverage 0.99` | доизвлечь признаки либо `--allow-missing` с честной оговоркой в работе |

Полный разбор — в [корневом README](../README.md#диагностика-проблем).
