# `src/` — код пайплайна

Весь исполняемый код проекта. Каждая стадия пайплайна запускается отсюда
**как модуль пакета** и **из корня проекта**:

```bash
uv run python -m src.<модуль> ...
```

Проект намеренно не устанавливается как пакет (`[tool.uv] package = false`):
у модулей относительные импорты (`from ..config import …`), то есть имя пакета —
буквально `src`. Поэтому `python src/data/manifest.py` сломается, а
`python -m src.data.manifest` работает.

## Что здесь лежит

### Файлы верхнего уровня

| Файл | Роль | Запуск |
|---|---|---|
| `config.py` | Единый конфиг: пути от корня проекта, seed, `device`/`batch_size`/`num_workers`. Единственное место, знающее про железо. | — |
| `train.py` | **Стадия 2** — обучение. Модель-агностичный цикл + тонкий YAML-раннер. | `python -m src.train --config …` |
| `evaluate.py` | **Стадия 3** — оценка. Инференс на тесте, метрики по каждому датасету. | `python -m src.evaluate --config …` |
| `doctor.py` | **Не стадия.** Проверка окружения и данных: версии пакетов, версия libsndfile, доступность CUDA, какие датасеты/манифесты/кэши есть на диске. | `python -m src.doctor` |

## Как устроен код: три интерфейса вместо ветвлений

Датасеты, признаки и модели в этом проекте **подбираются экспериментально**,
поэтому код нигде не «знает» заранее конкретный датасет, признак или модель.
Вместо ветвлений — три стабильных интерфейса:

1. **Манифест** (`data/schema.py`) — «любой датасет → пайплайн». Каноническая
   таблица с фиксированным набором колонок; всё датасет-специфичное живёт только
   в адаптере.
2. **Кэш признаков** (`data/features.py`) — «любые признаки → обучение».
   Per-file `.npy` с ключом (`dataset_id`, `utt_id`) + хэш конфига признаков.
3. **Контракт признак ↔ модель** (`data/dataset.py` + `models/model_base.py`) —
   «любые признаки → любая модель». Форма `[T, C]` float32, батч `[B, T, C]`
   + `lengths`, модель объявляет ожидаемое `C`.

### Правило не-ветвления

Ниже манифеста стадии читают **только канонические колонки**. Единственные
законные употребления `dataset_id` — `concat` (склейка манифестов) и `group-by`
(стратификация, разбивка метрик). Появление `if dataset_id == …` где-либо ниже
манифеста — это **code smell**: чинить надо схему, а не вставлять частный случай.

### Реестры

Три места используют одну и ту же схему «декоратор + таблица по имени»:

| Реестр | Где | Как добавить |
|---|---|---|
| Адаптеры датасетов | `data/sources/base.py` | новый модуль + `@register` + импорт в `sources/__init__.py` |
| Экстракторы признаков | `data/features.py` | новый класс + `@register_extractor` |
| Архитектуры моделей | `models/model_base.py` | новый класс + `@register_model` |

Выбор идёт по строковому имени из конфига, без if-цепочек. Добавление нового
элемента не требует правок ни в одной стадии.

## Конвенции кода

- **Память зависит от размера батча, а не от размера датасета.** Никогда не
  материализовать весь датасет или все признаки в один объект — всегда лениво
  с диска. `Dataset.__init__` держит только метаданные (id и метки как
  numpy-массивы), не данные: иначе каждый воркер `DataLoader` продублировал бы
  их в памяти.
- **Признаки — `float32`.** На CPU `float16` не ускоряет и плохо поддержан.
- **Перенос на устройство — ровно в одном месте:** цикл обучения делает
  `.to(device)` над собранным батчем. `Dataset` и коллатор работают на CPU и
  отдают обычные тензоры. Никакой «мультидевайсной абстракции» не строится.
- **Атомарная запись всего, что можно потом принять за готовое** — временный
  файл в той же папке, затем `os.replace`. Без этого проверка «файл существует →
  пропустить» небезопасна: падение посреди записи оставило бы битый файл.
- **Ошибки конфигурации ловятся до долгой работы.** Валидатор схемы на Стадии 0,
  проверка формы `[T, C]` на каждом выходе экстрактора, pre-flight сверка
  `C` (Стадия 2) и `feature_hash` (Стадия 3) — всё это дешёвые проверки, которые
  срабатывают раньше, чем начнётся дорогой прогон.
- **Раннеры стадий тонкие.** У каждой стадии свой `python -m`, глобального
  диспетчера нет. При нескольких датасетах раннер не падает на первом сбое:
  печатает ошибку, продолжает и в конце возвращает код `1` со списком неудавшихся.
