## 1. О проекте

- **Тема (магистерская работа):** Разработка метода выявления синтетической речи в аудио.
- **Суть задачи:** на основе обзора существующих работ найти, что можно улучшить, и реализовать это. Улучшение не обязано быть SOTA — достаточно нового ракурса с обоснованием.
- **Критерии защиты:**
  1. *Актуальность и научная новизна* — выводятся из обзора литературы (достаточно небольшого улучшения или нового подхода).
  2. *Доказуемость и измеримость* — чёткая структура, обоснованные шаги, каждый вывод подкреплён теоремой / научной работой / экспериментом.
- **Стадия работы:** практическая часть начата; основное направление **ещё не выбрано** — идут эксперименты с потенциальными направлениями.

### Связка ограничения и новизны (важно помнить)
Аппаратное ограничение «без GPU / лёгкий метод» — это одновременно **ниша новизны**. По обзору литературы проекта: SOTA достигается ценой SSL-моделей ~316M параметров, требующих GPU, и авторы сами признают это ограничением применимости. Поэтому «лёгкий метод под ограниченные ресурсы» — защитимый аргумент актуальности, а не только неудобство.

## 2. Жёсткие ограничения `[РЕШЕНО]`

- **Язык:** Python 3.12.3.
- **Обязательные библиотеки:** `numpy`, `librosa`, `pytorch`, `pandas`, `matplotlib`, `sklearn`. Остальные — по необходимости (вероятные кандидаты: `pyyaml` для конфигов, `h5py`/`pyarrow` для хранения, `tqdm`).
- **Главное ограничение по ресурсам:** эксперименты идут на ноутбуке **без GPU, на CPU**, RAM ограничена. Прогоны длительные. Пайплайн обязан переживать долгие прогоны **без падений по нехватке памяти**.

---

## 3. Архитектурная философия (почему всё устроено именно так)

**Главный принцип против OOM:** пиковое потребление RAM должно зависеть от **размера батча, а не от размера датасета.**

Из этого следует всё остальное:

1. **Стадийность с кэшем на диск.** Обработка разнесена на независимые стадии; промежуточные результаты лежат на диске, в памяти держится только текущая порция.
2. **Признаки считаются один раз и кэшируются.** Извлечение признаков из аудио — самый дорогой шаг на CPU; он платится один раз, дальше эксперименты читают готовый кэш.
3. **Возобновляемость (resumability).** Длинная стадия должна при перезапуске пропускать уже обработанные файлы (а не начинать заново). Критично именно из-за CPU.
4. **Развязанность = сравнимость экспериментов.** Смена «направления» — это замена одного модуля (признаки или модель) без переписывания остального. Это же обслуживает критерий №2 (измеримость): каждая стадия логируется отдельно.

## 4. Стадии пайплайна `[РЕШЕНО]` (структура; наполнение зависит от §9)

| Стадия | Модуль | Что делает | Читает | Пишет (артефакт) |
|---|---|---|---|---|
| 0. Индексация | `src/data/manifest.py` | Один проход по датасету, собирает метаданные. **Аудио не загружает.** | сырое аудио (только пути/метаданные) | манифест `.parquet` |
| 1. Признаки | `src/data/features.py` | Файл за файлом извлекает признаки, сразу пишет на диск. Самый дорогой шаг, возобновляемый. | манифест | кэш признаков (`.npy`/`.h5`/memmap) |
| 2. Обучение | `src/train.py` | Обучение модели; ленивая подгрузка признаков через `Dataset`/`DataLoader`. **В RAM только батч.** | кэш признаков | веса модели + построчный лог метрик по эпохам |
| 3. Оценка | `src/evaluate.py` | Инференс на тесте, метрики. | веса + кэш признаков | выгрузка скоров `.parquet` |

> Каждая стадия запускается **независимо**, по контракту `run(config)`.
> **Единой точки входа (CLI/`main.py`) сознательно нет** `[РЕШЕНО]` — стадии гоняются по отдельности (стадия 1 один раз и дорого; стадии 2–3 — многократно). При желании можно добавить тонкий диспетчер позже, но это не требуется.

## 6. Контракт артефактов (что пишут стадии, что читают ноутбуки) `[РЕШЕНО]`

Ноутбуки и `viz`-модули **ничего не пересчитывают** — они читают готовые артефакты с диска. Чтобы им было что читать, стадии обязаны эти артефакты писать:

- **Манифест** (`data/manifests/*.parquet`): путь, метка, сплит, длительность, тип атаки. → читает ноутбук датасета.
- **Кэш признаков** (`data/features/`): по одному объекту на файл или единый массив; формат зависит от железа (§9). → читает `dataset.py` и ноутбук аудиопризнаков (последний — на горстке примеров, не на всём датасете).
- **Лог метрик обучения** (например `experiments/<exp>/metrics.jsonl` или CSV): построчно по эпохам — эпоха, loss, val-EER, lr. → читает ноутбук обучения.
- **Выгрузка скоров** (`experiments/<exp>/scores.parquet`): предсказания/скоры по примерам теста (+ тип атаки). → читает ноутбук результатов.

## 7. Конвенции и правила гигиены `[РЕШЕНО]`

- **dtype:** держать признаки в `float32`, не `float64` (вдвое меньше памяти; `librosa.load` по умолчанию даёт `float32`).
- **Хранение больших матриц:** при нехватке RAM — `np.memmap` или HDF5 (чтение среза без загрузки всего массива).
- **`DataLoader`:** `num_workers` подбирать осторожно — на CPU обучение и загрузка конкурируют за те же ядра; «максимум воркеров» не всегда быстрее.
- **Воспроизводимость:** фиксировать seed; все параметры запуска — в конфиг-файле (`experiments/<exp>.yaml`), чтобы прогон можно было повторить и приложить к работе.
- **Ноутбуки тонкие:** логика — в `src/viz/`, ноутбук только импортирует, вызывает, сохраняет. Каждый ноутбук обязан проходить **Restart & Run All** сверху вниз без ошибок (иначе он не воспроизводим).
- **Фигуры для печати:** единый стиль через `src/viz/style.py`; линейные графики (loss, DET, ROC) — в **вектор** (PDF/SVG); спектрограммы/тепловые карты — растр с DPI ≥ 300. Экспорт — в `reports/figures/`.

## 8. Доменные заметки (специфика анти-спуфинга)

- **Основная метрика — EER** (Equal Error Rate); в литературе проекта она сквозная. Дополнительно встречается t-DCF.
- **Для графика результатов** стандарт — **DET-кривая** (detection error tradeoff), по которой читается EER; плюс матрица ошибок.
- **Разбивка EER по отдельным атакам** ценится комиссией: агрегированная метрика скрывает, на каких именно атаках метод проседает. В нескольких работах обзора это прямо отмечено как слабость — значит, такая разбивка = лёгкий измеримый вклад.
- **Кандидаты признаков из обзора** (для контекста, не финальный выбор): ручные кепстральные (LFCC, MFCC, CQCC), мел-спектрограммы под CNN, просодика (F0/энергия/длительность), SSL-эмбеддинги (wav2vec2/HuBERT/WavLM — тяжёлые, на CPU очень медленные).

## 10. Журнал ключевых решений

- Пайплайн разнесён на стадии 0–3 с кэшем на диск — ради RAM-безопасности и сравнимости экспериментов.
- Единая точка входа отклонена — стадии запускаются независимо.
- Графики: 4 тонких ноутбука (признаки / датасет / обучение / результаты), вся логика — в `src/viz/`.
- Контракт артефактов зафиксирован: стадии пишут манифест / кэш / лог метрик / скоры, ноутбуки только читают.
