## 1. О проекте

- **Тема (магистерская работа):** Разработка метода выявления синтетической речи в аудио.
- **Суть задачи:** на основе обзора существующих работ найти, что можно улучшить, и реализовать это. Улучшение не обязано быть SOTA — достаточно нового ракурса с обоснованием.
- **Критерии защиты:**
  1. *Актуальность и научная новизна* — выводятся из обзора литературы (достаточно небольшого улучшения или нового подхода).
  2. *Доказуемость и измеримость* — чёткая структура, обоснованные шаги, каждый вывод подкреплён теоремой / научной работой / экспериментом.
- **Стадия работы:** практическая часть начата; основное направление **ещё не выбрано** — идут эксперименты с потенциальными направлениями.

### Связка ограничения и новизны (важно помнить)
Аппаратное ограничение «без GPU / лёгкий метод» — это одновременно **ниша новизны**. По обзору литературы проекта: SOTA достигается ценой SSL-моделей ~316M параметров, требующих GPU, и авторы сами признают это ограничением применимости. Поэтому «лёгкий метод под ограниченные ресурсы» — защитимый аргумент актуальности, а не только неудобство.

- **Язык:** Python 3.12.3.
- **Обязательные библиотеки:** `numpy`, `librosa`, `pytorch`, `pandas`, `matplotlib`, `sklearn`. Остальные — по необходимости (вероятные кандидаты: `pyyaml` для конфигов, `h5py`/`pyarrow` для хранения, `tqdm`).

## 3. Архитектурная философия (почему всё устроено именно так)

**Главный принцип против OOM:** пиковое потребление RAM должно зависеть от **размера батча, а не от размера датасета.**

Из этого следует всё остальное:

1. **Стадийность с кэшем на диск.** Обработка разнесена на независимые стадии; промежуточные результаты лежат на диске, в памяти держится только текущая порция.
2. **Признаки считаются один раз и кэшируются.** Извлечение признаков из аудио — самый дорогой шаг на CPU; он платится один раз, дальше эксперименты читают готовый кэш.
3. **Возобновляемость (resumability).** Длинная стадия должна при перезапуске пропускать уже обработанные файлы (а не начинать заново). Критично именно из-за CPU.
4. **Развязанность = сравнимость экспериментов.** Смена «направления» — это замена одного модуля (признаки или модель) без переписывания остального. Это же обслуживает критерий №2 (измеримость): каждая стадия логируется отдельно.
5. **Агностичность по трём осям `[РЕШЕНО как требование]`.** Датасеты, признаки и модели подбираются экспериментально → система не должна «знать» заранее конкретный датасет/признак/модель. Стабильные интерфейсы между сменными частями: **манифест** (любой датасет → пайплайн) и **кэш признаков** (любые признаки → обучение).

### Бюджет памяти (потолок 5 ГБ) — где реально риск
Из 5 ГБ часть уже занимает базовый процесс: импорт `torch`/`numpy`/`librosa` резидентно — обычно сотни МБ (*оценка, не точный факт — стоит измерить на машине через `psutil`*). Реальный бюджет под данные/модель ≈ 3.5–4 ГБ; проектировать с запасом. Риск OOM концентрируется **не** в стадии 1:
- **Стадия 1 безопасна по RAM.** Один аудиофайл во `float32` — единицы–десятки МБ (5 мин при 16 кГц ≈ 18 МБ). Стадия 1 ограничена временем CPU и местом на диске, а не памятью.
- **Реальные источники OOM:** (а) случайная материализация всего датасета/матрицы признаков в один массив/`DataFrame`; (б) `DataLoader` с несколькими воркерами — каждый процесс дублирует память; (в) большой батч / удержание графа в обучении; (г) **загрузка тяжёлой модели**: SSL вроде wav2vec2/HuBERT ≈ 300M параметров ≈ **1.2 ГБ только веса** = четверть бюджета, и медленно на CPU → SSL-направление на этом железе маргинально (учитывать при выборе направления).

## 6. Контракт артефактов (что пишут стадии, что читают ноутбуки) `[РЕШЕНО]`

Ноутбуки и `viz`-модули **ничего не пересчитывают** — они читают готовые артефакты с диска. Чтобы им было что читать, стадии обязаны эти артефакты писать:

- **Манифест** (`data/manifests/*.parquet`): путь, метка, сплит, длительность, тип атаки. → читает ноутбук датасета.
- **Кэш признаков** (`data/features/`): по одному объекту на файл или единый массив; формат зависит от железа (§9). Путь кэша включает **id датасета + хэш конфига признаков** — чтобы разные наборы признаков не путались, а при возврате к уже посчитанному не было пересчёта. → читает `dataset.py` и ноутбук аудиопризнаков (последний — на горстке примеров, не на всём датасете).
- **Лог метрик обучения** (например `experiments/<exp>/metrics.jsonl` или CSV): построчно по эпохам — эпоха, loss, val-EER, lr. → читает ноутбук обучения.
- **Выгрузка скоров** (`experiments/<exp>/scores.parquet`): предсказания/скоры по примерам теста (+ тип атаки). → читает ноутбук результатов.

## 7. Конвенции и правила гигиены `[РЕШЕНО]`

### Память (потолок 5 ГБ)
- **Никогда** не материализовать весь датасет/все признаки в один объект в RAM. Всегда потоково / лениво с диска.
- **Кэш больше RAM → `np.memmap` или HDF5** срезами (резидентная память ограничена, ОС кеширует страницы). Для очень больших датасетов — **шардирование**: и обработка, и кэш по шардам, чтобы (а) не держать весь датасет разом и (б) возобновляемость работала на уровне шарда.
- **`Dataset.__init__` держит только манифест** (метаданные), не данные — иначе каждый воркер `DataLoader` дублирует это в памяти. Воркеров мало (0–2).
- **Маленький батч из-за памяти → накопление градиента** (gradient accumulation) для большего *эффективного* батча без роста RAM.
- **Контроль памяти:** лёгкое логирование RSS (`psutil`) на ключевых шагах, чтобы ловить рост заранее, а не в момент OOM.

### Возобновляемость после падения (механизм) `[РЕШЕНО]`
Требование: если стадия упала, обработав N%, рестарт продолжает с невыполненного, а не с нуля. Механизм **разный** для пакетных стадий и для обучения:

- **Стадии 1 и 3 (пакет по файлам) — паттерн «пропустить готовое».**
  - Детерминированный путь выхода на каждый вход (id файла + хэш конфига признаков).
  - Перед обработкой: если выход уже есть → пропустить.
  - **Атомарная запись (критично!):** писать во временный `*.tmp`, затем `os.replace(tmp, final)` (атомарно в пределах одной ФС). Иначе падение *посреди записи* оставит существующий, но битый файл, который будет ошибочно засчитан как готовый. Без атомарности проверка «существует → пропустить» небезопасна.
  - Шардированный вариант: тот же приём на уровне шарда + маркер `*.done`, записываемый атомарно последним.
- **Стадия 2 (обучение) — паттерн «чекпойнт».** «Пропустить готовое» неприменимо.
  - Периодически (каждые N шагов/эпох) сохранять чекпойнт: `state_dict` модели + состояние оптимизатора + scheduler + эпоха/шаг + состояния ГСЧ (`torch`/`numpy`/`random`).
  - При старте: есть свежий чекпойнт → загрузить и продолжить с него.
  - Та же атомарная запись (чекпойнты крупные, падение при сохранении их портит); держать последние K чекпойнтов (ротация), чтобы не остаться с единственным битым.
  - Лог метрик — в режиме дописывания; при возобновлении дедуплицировать по эпохе или обрезать до эпохи чекпойнта.
  - *Нюанс воспроизводимости:* бит-в-бит идентичность возобновлённого прогона неразорванному требует восстановления состояний ГСЧ. Для работы достаточно *валидного* прогона, но если нужна строгая воспроизводимость — ГСЧ обязателен.

- **dtype:** держать признаки в `float32`, не `float64` (вдвое меньше памяти; `librosa.load` по умолчанию даёт `float32`). На CPU `float16` не ускоряет и плохо поддержан — для вычислений оставаться в `float32`.
- **`DataLoader`:** `num_workers` подбирать осторожно — на CPU обучение и загрузка конкурируют за те же ядра; «максимум воркеров» не всегда быстрее.
- **Воспроизводимость:** фиксировать seed; все параметры запуска — в конфиг-файле (`experiments/<exp>.yaml`), чтобы прогон можно было повторить и приложить к работе.
- **Ноутбуки тонкие:** логика — в `src/viz/`, ноутбук только импортирует, вызывает, сохраняет. Каждый ноутбук обязан проходить **Restart & Run All** сверху вниз без ошибок (иначе он не воспроизводим).
- **Фигуры для печати:** единый стиль через `src/viz/style.py`; линейные графики (loss, DET, ROC) — в **вектор** (PDF/SVG); спектрограммы/тепловые карты — растр с DPI ≥ 300. Экспорт — в `reports/figures/`.

## 8. Доменные заметки (специфика анти-спуфинга)

- **Основная метрика — EER** (Equal Error Rate); в литературе проекта она сквозная. Дополнительно встречается t-DCF.
- **Для графика результатов** стандарт — **DET-кривая** (detection error tradeoff), по которой читается EER; плюс матрица ошибок.
- **Разбивка EER по отдельным атакам** ценится комиссией: агрегированная метрика скрывает, на каких именно атаках метод проседает. В нескольких работах обзора это прямо отмечено как слабость — значит, такая разбивка = лёгкий измеримый вклад.
- **Кандидаты признаков из обзора** (для контекста, не финальный выбор): ручные кепстральные (LFCC, MFCC, CQCC), мел-спектрограммы под CNN, просодика (F0/энергия/длительность), SSL-эмбеддинги (wav2vec2/HuBERT/WavLM — тяжёлые, на CPU очень медленные).

## 10. Журнал ключевых решений

- Пайплайн разнесён на стадии 0–3 с кэшем на диск — ради RAM-безопасности и сравнимости экспериментов.
- Единая точка входа отклонена — стадии запускаются независимо.
- Графики: 4 тонких ноутбука (признаки / датасет / обучение / результаты), вся логика — в `src/viz/`.
- Контракт артефактов зафиксирован: стадии пишут манифест / кэш / лог метрик / скоры, ноутбуки только читают.
- Потолок RAM 5 ГБ зафиксирован → дисковый потоковый дизайн обязателен; добавлены правила бюджета памяти (§3, §7); SSL-признаки помечены как маргинальные на этом железе.
- Введён слой адаптеров датасетов (`src/data/sources/`) — манифест как универсальный интерфейс «любой датасет → пайплайн» (ответ на «датасеты разные»).
- `features.py` и `models/` оформлены как реестры с общими интерфейсами (агностичность под экспериментальный подбор признаков и моделей); кэш ключуется по конфигу признаков.
- Механизм возобновляемости конкретизирован (§7): пакетные стадии — «пропустить готовое» + **атомарная запись** (защита от битых файлов при падении в момент записи); обучение — периодические чекпойнты с ротацией и состояниями ГСЧ.
