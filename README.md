# Выявление синтетической речи в аудио

Исследовательский пайплайн для магистерской работы: обнаружение синтезированной
(«спуфинговой») речи в аудиозаписях. Проект устроен как **лёгкий метод под
ограниченные ресурсы** — модель должна быть дёшева в развёртывании и инференсе,
а не гнаться за SOTA ценой SSL-моделей на сотни миллионов параметров.

Основная метрика — **EER** (Equal Error Rate). Пайплайн разнесён на четыре
независимые стадии с кэшированием промежуточных результатов на диск; каждая
стадия возобновляема после обрыва.

> **Где что читать.** Этот файл — про запуск и эксплуатацию. Про то, *почему*
> архитектура именно такая (обоснования решений, открытые вопросы, changelog),
> — в [`PROJECT_ARCHITECTURE.md`](PROJECT_ARCHITECTURE.md). Ссылки вида «§6.1»
> по тексту ведут туда.

## Быстрый старт

```bash
# 1. окружение (машина без NVIDIA GPU)
uv sync --extra cpu

# 2. проверка окружения и данных
uv run python -m src.doctor

# 3. Стадия 0 — построить манифест датасета
uv run python -m src.data.manifest asvspoof2019_la

# 4. Стадия 1 — извлечь признаки в кэш (самый долгий шаг)
uv run python -m src.data.features asvspoof2019_la -f lfcc

# 5. Стадия 2 — обучить
uv run python -m src.train --config experiments/smoke_lfcc_statpool.yaml

# 6. Стадия 3 — оценить
uv run python -m src.evaluate --config experiments/smoke_lfcc_statpool.yaml
```

Все команды выполняются **из корня проекта** (папка, где лежит `src/`).

## Установка

### Требования

| Что | Версия | Комментарий |
|---|---|---|
| Python | 3.12 | задан в `.python-version`; `uv` скачает сам, ставить отдельно не нужно |
| `uv` | любая свежая | менеджер окружения, см. [docs.astral.sh/uv](https://docs.astral.sh/uv/) |
| `ffmpeg` | опционально | запасной декодер аудио; при `soundfile 0.12.1` на текущих датасетах не задействуется |

Больше системных зависимостей нет.

### Установка окружения

```bash
uv sync --extra cpu     # машина без NVIDIA GPU
uv sync --extra gpu     # машина с NVIDIA GPU (CUDA 13)
```

Затем обязательно:

```bash
uv run python -m src.doctor
```

`doctor` — не стадия пайплайна, а сервисная проверка: версии пакетов, версия
libsndfile, доступность CUDA, какие датасеты/манифесты/кэши реально есть на диске.
Возвращает код `1`, если чего-то обязательного не хватает.

### Почему `torch` в экстрах, а не выбирается сам

Маркеры платформы в `pyproject.toml` различают операционную систему, но **не**
наличие видеокарты. По умолчанию PyPI отдаёт CPU-сборку на Windows и CUDA-сборку
на Linux — то есть Windows + NVIDIA молча получил бы `torch` без CUDA. Поэтому
выбор сделан явным: конфликтующие экстры `cpu` / `gpu`, обе резолюции лежат в
одном `uv.lock`. Ошибиться не страшно — `doctor` печатает
`torch.cuda.is_available()` и предупреждает о рассинхроне.

### ⚠️ `soundfile` жёстко закреплён на `0.12.1`

Это **единственный точный пин** в проекте, и его нельзя снимать «на всякий случай».

`soundfile 0.12.1` несёт libsndfile **1.2.0**. Более новый libsndfile **1.2.2**
не декодирует часть валидных FLAC-файлов ASVspoof 2021 (баг его FLAC-декодера:
`lost sync` / `unknown error`), при этом заголовок через `sf.info` читается
нормально — из-за чего проблема выглядит не как проблема декодера. Любой
`uv add -U soundfile` вернёт этот баг, а увидите вы его только через час прогона
Стадии 1 по строкам в `_failures.csv`. `doctor` проверяет версию libsndfile
отдельным пунктом именно поэтому.

### Запуск команд

```bash
uv run python -m src.<модуль> ...
```

`uv run` сам подхватывает окружение и досинхронизирует его по локфайлу — активировать
`.venv` не нужно. Для длинной сессии можно один раз активировать вручную
(`source .venv/bin/activate`, в Windows `.venv\Scripts\activate`) и дальше писать
команды без префикса `uv run`.

**Важно:** проект намеренно **не устанавливается как пакет** (`[tool.uv] package = false`) —
у модулей относительные импорты, имя пакета буквально `src`. Отсюда жёсткое правило:
запуск только через `python -m src.<модуль>` и только из корня проекта.
`python src/data/manifest.py` сломается — это не баг, а следствие.

### Правки зависимостей

- новая библиотека → `uv add <pkg>` (сам правит `pyproject.toml` и `uv.lock`);
- ручная правка `pyproject.toml` → затем `uv lock`;
- `uv.lock` **коммитится всегда** — это и есть фиксация среды для воспроизводимости;
- запасной путь без `uv`: `uv export --extra cpu --no-hashes -o requirements.txt`
  (производный артефакт, источник истины — `pyproject.toml` + `uv.lock`).

## Стадии пайплайна

| Стадия | Команда | Читает | Пишет |
|---|---|---|---|
| 0. Индексация | `python -m src.data.manifest` | пути/метаданные аудио | `data/manifests/<ds>.parquet` |
| 1. Признаки | `python -m src.data.features` | манифест + аудио | `data/features/<feat>-<hash>/` |
| 2. Обучение | `python -m src.train` | кэш признаков | `experiments/<exp>/*.pt`, `metrics.jsonl` |
| 3. Оценка | `python -m src.evaluate` | веса + кэш признаков | `scores.parquet`, `eval_metrics.json` |

**Единой точки входа (`main.py`) сознательно нет.** Стадии независимы и гоняются
с разной частотой: Стадия 1 — один раз и дорого, Стадии 2–3 — многократно.

---

### Стадия 0 — индексация

Один проход по датасету: собирается таблица «путь → метка → сплит → метаданные».
**Аудио не загружается**, только пути и метаданные, поэтому память не растёт.

```bash
# один датасет
uv run python -m src.data.manifest for-2seconds

# несколько сразу
uv run python -m src.data.manifest asvspoof2019_la asvspoof2021_la asvspoof2021_df

# все зарегистрированные адаптеры
uv run python -m src.data.manifest --all

# показать доступные dataset_id и выйти
uv run python -m src.data.manifest --list
```

| Флаг | Назначение |
|---|---|
| `datasets` (позиционные) | один или несколько `dataset_id` (= имена папок в `data/raw/`) |
| `--all` | обработать все зарегистрированные адаптеры |
| `--list` | показать доступные `dataset_id` и выйти |
| `--root PATH` | задать корень проекта вручную (нужно только при нестандартном расположении) |

**Особенности:**

- Первый прогон делайте **по одному датасету** — так изолируется возможный сбой
  (внешние файлы с ключами у наборов 2021, формат протокола 2019 и т.п.).
- 2021 LA/DF — сотни тысяч файлов: обход папки занимает заметное время, но аудио
  не читается.
- ASVspoof 2021 DF даёт **меньше** строк, чем полный eval: скачан намеренно только
  `part00` из трёх. Это решение, а не недокачка — так и отчитывается в работе.
- ASVspoof 2019 LA индексируется по CM-протоколу; ASV-enrollment записи из папок
  `dev`/`eval` (файлы вида `LA_D_A…`) в манифест **не входят**.
- При нескольких датасетах раннер не падает на первом сбое: печатает
  `[<ds>] ОШИБКА: …`, продолжает остальные и в конце возвращает код `1` со списком
  неудавшихся.

После прогона печатается сводка (число строк, разбивка `split × label`,
заполненность `attack_type`/`speaker_id`) — это сразу санити-проверка.

### Стадия 1 — признаки

Файл за файлом: декодирование аудио → извлечение признаков `[T, C]` → атомарная
запись `.npy` в кэш. Самый дорогой по времени шаг, платится один раз.

```bash
# один датасет, один экстрактор
uv run python -m src.data.features asvspoof2019_la -f lfcc

# несколько датасетов (экстрактор всё равно один на прогон)
uv run python -m src.data.features asvspoof2021_la asvspoof2021_df -f lfcc

# все датасеты, у которых уже построен манифест
uv run python -m src.data.features --all -f logmel

# показать экстракторы (с C / sr / хэшем) и датасеты, выйти
uv run python -m src.data.features --list

# быстрый smoke на первых N примерах
uv run python -m src.data.features for-2seconds -f lfcc --limit 200
```

| Флаг | Назначение |
|---|---|
| `datasets` (позиционные) | один/несколько `dataset_id`; манифест должен существовать |
| `-f`, `--features NAME` | какой экстрактор; **один на прогон** |
| `--all` | все датасеты с готовым манифестом |
| `--list` | показать экстракторы и датасеты, выйти |
| `--limit N` | только первые N (стабильно отсортированных) примеров — smoke, **не** для итоговых метрик |
| `--root PATH` | корень проекта вручную |

**Раскладка кэша:** `data/features/<name>-<hash>/<dataset_id>/<utt_id>.npy`,
где `hash` — короткий sha1 от конфига признаков.

**Особенности:**

- Разные параметры экстрактора → разный хэш → **разные папки кэша**. Наборы не
  путаются, а возврат к прежним параметрам не вызывает пересчёта.
- `logmel` считать только когда он реально понадобится — иначе зря занятые
  гигабайты на диске.
- Единичный битый файл **не роняет прогон**: он логируется в
  `<dataset_id>/_failures.csv` с реальной причиной. Систематический сбой
  (0 успехов на непустом входе) помечает датасет как неудавшийся.
- Рядом с кэшем пишется `_spec.json` — паспорт папки: все параметры признака и
  версии библиотек. Это и есть фиксация воспроизводимости на уровне признаков.
- Итоговый EER берётся на **полном** тесте, не на `--limit`-подвыборке.

### Стадия 2 — обучение

```bash
# показать зарегистрированные признаки и модели, выйти
uv run python -m src.train --list

# запустить прогон
uv run python -m src.train --config experiments/smoke_lfcc_statpool.yaml
```

| Флаг | Назначение |
|---|---|
| `--config PATH` | `experiments/<exp>.yaml` — полное описание прогона (обязателен, кроме `--list`) |
| `--list` | показать доступные признаки/модели и выйти |
| `--root PATH` | корень проекта вручную |

**Что происходит.** Резолвится признак → его `C` и папка кэша. **Pre-flight**
сверяет `C` из `_spec.json` кэша с `C`, который объявляет модель: рассинхрон
«признак ≠ модель» и отсутствие кэша ловятся **до** долгого обучения, с внятной
ошибкой и подсказкой про Стадию 1. Дальше — чтение манифестов по селекторам,
опциональная подвыборка, ленивая загрузка признаков (в памяти только батч),
обучение; в конце каждой эпохи считается val-EER, пишутся строка в `metrics.jsonl`
и чекпойнт.

**Предусловия:**

1. Манифест датасета(ов) построен (Стадия 0).
2. Кэш признака покрывает те примеры, что попадут в подвыборку.

Полный прогон Стадии 1 при этом **не обязателен** — Стадия 2 читает `.npy` по
ключу (`dataset_id`, `utt_id`) и отфильтровывает отсутствующие с предупреждением.

> **Тонкость про smoke.** `features --limit N` берёт **первые N** после стабильной
> сортировки, а подвыборка обучения берёт **стратифицированные по seed** примеры —
> это разные множества, и они могут почти не пересечься. Надёжный smoke: либо
> полный кэш признака, либо согласуйте охват вручную.

### Стадия 3 — оценка

Использует **тот же самый** YAML-конфиг, что и обучение — читает секции
`data.test`, `data.subset.n_test` и `eval.*` (Стадия 2 их игнорирует). Отсюда
следует, что рассинхрон «оценили не тем, чем учили» невозможен по построению.

```bash
# оценка по конфигу (веса — из eval.weights, по умолчанию best.pt)
uv run python -m src.evaluate --config experiments/smoke_lfcc_statpool.yaml

# явно выбрать веса
uv run python -m src.evaluate --config experiments/<exp>.yaml --weights final
uv run python -m src.evaluate --config experiments/<exp>.yaml --weights experiments/<exp>/ckpt_epoch0007.pt

# посчитать при неполном кэше признаков (осознанно)
uv run python -m src.evaluate --config experiments/<exp>.yaml --allow-missing
```

| Флаг | Назначение |
|---|---|
| `--config PATH` | тот же файл, что у Стадии 2 (обязателен, кроме `--list`) |
| `--weights` | `best` \| `final` \| путь к `.pt`; переопределяет `eval.weights` |
| `--allow-missing` | не падать при покрытии кэша ниже `eval.min_coverage` |
| `--list` | показать доступные признаки/модели и выйти |
| `--root PATH` | корень проекта вручную |

**Что происходит.** Модель восстанавливается **по метаданным чекпойнта**
(`model_name`, `model_params`, `in_channels`, `t_fixed`), а не по YAML: оценка
идёт той же архитектурой и с тем же входом, что были при обучении. Pre-flight
здесь **строже**, чем на Стадии 2: помимо `C` сверяется `feature_hash` из
чекпойнта — так ловится случай «`C` совпал (60 = 60), а параметры признака другие»,
который одной сверкой `C` не отличить.

**Метрики считаются по каждому датасету отдельно.** Общего EER по смеси нет
намеренно: он смешал бы разные домены и разные классовые пропорции в одно
неинтерпретируемое число. Кросс-датасетный вывод читается сравнением строк.

**Предусловия:** прогнана Стадия 2 (есть `best.pt`/`final.pt`) и кэш признака
покрывает тестовые примеры. Неполное покрытие меняет знаменатель метрики,
поэтому оно не замалчивается: доля пишется в `eval_metrics.json`, а падение ниже
`eval.min_coverage` роняет прогон.

## Конфигурация прогона

Два уровня, не конкурирующих между собой:

- **`src/config.py`** — статика: пути от корня проекта, seed, дефолты среды
  (`device`, `batch_size`, `num_workers`). Это единственное место, знающее про железо.
- **`experiments/<exp>.yaml`** — один файл на прогон, описывает и обучение, и
  оценку. Секция `runtime` переопределяет дефолты `config.py`.

Готовый пример со всеми секциями и комментариями —
[`experiments/smoke_lfcc_statpool.yaml`](experiments/smoke_lfcc_statpool.yaml);
разбор полей — в [`experiments/README.md`](experiments/README.md).

Профиль по умолчанию в примере — **smoke**: маленькая стратифицированная
подвыборка и пара эпох, чтобы за минуты убедиться, что цикл, чекпойнты, лог и
val-EER живы. **Полный прогон = убрать секцию `data.subset`** — тот же код, тот
же кэш.

## Возобновляемость

Прогоны на CPU длительные, поэтому стадия, прерванная на N %, при рестарте
**той же командой** продолжает с невыполненного, а не с нуля. Механизм разный:

- **Стадия 1 — «пропустить готовое».** Путь выхода детерминирован по
  (`dataset_id`, `utt_id`) + хэш конфига признаков; файл есть → пропуск. Запись
  атомарная (временный файл + `os.replace`), иначе падение посреди записи
  оставило бы битый `.npy`, ошибочно засчитанный как готовый.
- **Стадия 2 — «чекпойнт».** Периодически (каждые `ckpt_every` эпох) сохраняется
  модель + оптимизатор + эпоха; при старте подхватывается свежий чекпойнт.
  Ротация держит последние `keep_last` (значение клампится к ≥ 1 — без чекпойнта
  нет resume). `metrics.jsonl` дописывается и дедуплицируется по эпохе.
- **Стадия 3 — шарды.** Скоры пишутся порциями по `eval.shard_rows` строк в
  `scores_parts/part_NNNNN.parquet`; при рестарте уже посчитанные ключи
  исключаются, в конце шарды склеиваются и удаляются. Рядом лежит `_state.json` —
  **отпечаток условий** прогона (веса, эпоха, `feature_hash`, `t_fixed`, окно,
  селекторы, подвыборка). Изменились условия → старые шарды удаляются с
  предупреждением, а не смешиваются с новыми. Это штатный сценарий, не ошибка.

## Диагностика проблем

Первое действие при любой странности:

```bash
uv run python -m src.doctor
```

### Запуск и импорты

| Симптом | Причина | Что делать |
|---|---|---|
| `ModuleNotFoundError: No module named 'src'` | запуск не из корня проекта | `cd` в папку, где лежит `src/`, и повторить |
| `ImportError: attempted relative import…` | запуск файлом, а не модулем | только `python -m src.<модуль>`, не `python src/.../x.py` |
| `нужен PyYAML для чтения конфигов…` | окружение не синхронизировано | `uv sync --extra cpu` (или `gpu`) |
| `torch.cuda.is_available() == False` при наличии GPU | поставлен экстра `cpu` | `uv sync --extra gpu` |

### Данные и стадии

| Сообщение | Что значит | Что делать |
|---|---|---|
| `нет манифеста … — сначала Стадия 0` | не построен индекс датасета | `python -m src.data.manifest <ds>` |
| `нет кэша признаков … (_spec.json отсутствует)` | не считались признаки этой конфигурации | `python -m src.data.features <ds> -f <feat>` |
| `в кэше … нет ни одного файла из манифеста` | кэш пуст или собран для другого датасета | проверьте, что Стадия 1 гонялась по тем же `dataset_id` |
| `ВНИМАНИЕ: N/M примеров без .npy …` | кэш покрывает манифест частично | доизвлеките признаки либо примите неполноту осознанно |
| `[<ds>] ОШИБКА: …` в конце прогона | сбой на одном датасете из нескольких | остальные обработаны; смотрите текст ошибки этого датасета |

### Рассинхрон «признак ↔ модель»

| Сообщение | Что значит | Что делать |
|---|---|---|
| `C кэша (X) ≠ C признака <name> (Y)` | папка кэша собрана другим конфигом признаков | приведите секцию `feature` в YAML к конфигу кэша либо пересчитайте Стадию 1 |
| `модель обучена на признаке с хэшем …, а в конфиге … даёт …` | `C` совпал, но параметры признака другие — оценка шла бы на **других** признаках | приведите секцию `feature` в YAML к конфигу обучения |
| `ВНИМАНИЕ: в чекпойнте нет model_params (старый формат)` | чекпойнт записан до появления поля | модель соберётся на дефолтах; при отличии от конфига обучения упадёт `load_state_dict` — переобучите или укажите дефолтные гиперпараметры |

### Стадия 3

| Сообщение | Что значит | Что делать |
|---|---|---|
| `нет весов … — сначала Стадия 2` | не прогнано обучение или запрошены не те веса | прогоните Стадию 2 либо укажите `--weights final` / путь |
| `нет папки эксперимента …` | `name` в YAML не соответствует ни одному прогону | сверьте `name` с содержимым `experiments/` |
| `в конфиге нет data.test` | отсутствует секция тестовых селекторов | добавьте `test: - {dataset_id: …, split: test}` |
| `eval.window='full' не реализован` | поддержано только окно `fixed` | оставьте `window: fixed` (см. «сознательно отложено» в архдокументе) |
| `покрытие 0.97 < min_coverage 0.99` | метрика считалась бы по неполному тесту | доизвлеките признаки либо `--allow-missing` и **честно оговорите покрытие в работе** |
| `условия прогона изменились, шарды удалены` | сменились веса/тест/признак при живых шардах | это нормально: пересчёт с нуля вместо тихого смешивания скоров двух прогонов |

### Аудио и декодирование

| Симптом | Причина | Что делать |
|---|---|---|
| Массовые записи в `_failures.csv` с `lost sync` / `unknown error` на FLAC 2021 | обновился libsndfile до 1.2.2 | вернуть `soundfile==0.12.1` (`uv sync`), см. раздел про пин выше |
| Единичные записи в `_failures.csv` | битый или нестандартный файл | нормально, прогон не роняется; при желании — поставить `ffmpeg` для фолбэка |
| `сигнал слишком короткий для дельт: T=…` | запись короче окна дельта-коэффициентов LFCC | файл честно попадает в `_failures.csv`; вмешательство обычно не требуется |

### Память и производительность

| Симптом | Что делать |
|---|---|
| Процесс убит по памяти на Стадии 2/3 | уменьшить `runtime.batch_size`; поставить `runtime.num_workers: 0` (каждый воркер дублирует память) |

| Стадия 1 идёт очень долго | это ожидаемо — она платится один раз; прогон возобновляем, можно прерывать |

## Конвенции, которые легко перепутать

- **Метка:** `spoof = 1`, `bonafide = 0`. Положительный класс — детектируемая
  синтетика. Едино для всех адаптеров.
- **Скор:** сырой логит, **больше ⇒ спуф**. ⚠️ В официальных протоколах ASVspoof
  CM-скор ориентирован **обратно** (больше ⇒ bonafide): при сравнении с чужими
  скор-файлами знак надо инвертировать. Конвенция записана в `eval_metrics.json`,
  чтобы число нельзя было прочитать наоборот.
- **Отсутствующее поле — явный NULL**, а не строка `"unknown"`: нужно отличать
  «поля нет в датасете» от «поле есть, но значение неизвестно».
- **Глобальный ключ примера** — пара (`dataset_id`, `utt_id`). Имена файлов между
  датасетами могут совпадать, поэтому одного `utt_id` мало.
- **Метрики — по каждому датасету отдельно.** Общего EER по смеси нет намеренно.
- **Две рабочие точки матрицы ошибок:** `at_val_threshold` (порог выбран на
  валидации до теста — честная точка) и `at_eer_threshold` (порог подобран на
  самом тесте — иллюстрация, **не** оценка обобщения). Не путать их в тексте работы.
- **Подвыборки — для итерации и отладки.** Итоговый EER берётся на полном тесте:
  на малом тесте оценка EER имеет высокую дисперсию, а порог определён плохо.
