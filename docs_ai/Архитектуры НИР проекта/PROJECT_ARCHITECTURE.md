## 1. О проекте

- **Тема (магистерская работа):** Разработка метода выявления синтетической речи в аудио.
- **Суть задачи:** на основе обзора существующих работ найти, что можно улучшить, и реализовать это. Улучшение не обязано быть SOTA — достаточно нового ракурса с обоснованием.
- **Критерии защиты:**
  1. *Актуальность и научная новизна* — выводятся из обзора литературы (достаточно небольшого улучшения или нового подхода).
  2. *Доказуемость и измеримость* — чёткая структура, обоснованные шаги, каждый вывод подкреплён теоремой / научной работой / экспериментом.
- **Стадия работы:** практическая часть начата; основное направление **ещё не выбрано** — идут эксперименты с потенциальными направлениями.

### Связка «лёгкость метода → новизна» (важно помнить)
Новизна проекта — в том, что **метод лёгкий**: дёшев в развёртывании и инференсе на ограниченных ресурсах. По обзору литературы проекта SOTA достигается ценой SSL-моделей ~316M параметров, требующих GPU, и авторы сами признают это ограничением применимости. Поэтому «лёгкий метод под ограниченные ресурсы» — защитимый аргумент актуальности.

**Разводить две вещи** (иначе теряется аргумент новизны):
- *На чём метод обучается* — **переменная**. Сейчас это CPU-ноутбук; маловероятно, но возможно предоставление GPU-машины. Железо разработки к научной ценности отношения не имеет.
- *Какой у метода вес* — **это и есть вклад**. Ценность лёгкости — в дешёвом *развёртывании/инференсе*, а не в том, на каком железе шло обучение.
- **Риск при появлении GPU** (не архитектурный, а дисциплинарный): соблазн взять тяжёлый SSL «потому что теперь можно» — и тогда лёгкость как ракурс новизны теряется. Даже с GPU итоговый метод держать лёгким. Формулировать защиту научно («лёгкие методы важны для реального развёртывания»), а не «у меня слабый ноутбук».

## 2. Жёсткие ограничения `[РЕШЕНО]`

- **Язык:** Python 3.12.3.
- **Обязательные библиотеки:** `numpy`, `librosa`, `pytorch`, `pandas`, `matplotlib`, `sklearn`, `pyarrow` — движок чтения/записи `.parquet` (формат манифестов и выгрузки скоров, §4–§6; без него `pandas.to_parquet`/`read_parquet` не работают), `pyyaml` — чтение конфигов Стадий 2–3 (`experiments/<exp>.yaml`; **подтверждено на Стадиях 2–3**), `scipy` — DCT в `lfcc` (Стадия 1) и нормально-вероятностная шкала DET-кривой (`viz/results.py`). Остальные — по необходимости (`tqdm` для прогресса, `psutil` для контроля памяти).
- **Декодирование аудио / фиксация версии `soundfile` `[РЕШЕНО]`.** `librosa` читает аудио через `soundfile` (libsndfile). Зафиксировано `soundfile==0.12.1` (несёт libsndfile **1.2.0**). Причина — *факт, проверенный на данных*: libsndfile **1.2.2** не декодирует часть валидных FLAC ASVspoof 2021 (ошибка его FLAC-декодера «lost sync» / «unknown error»; при этом заголовок `sf.info` читается — что и путало диагностику), а 1.2.0 эти файлы декодирует. Любой `pip install -U soundfile` вернёт баг — **не обновлять** без перепроверки; это важно для воспроизводимости среды (критерий №2). Как страховку Стадия 1 умеет фолбэк на `ffmpeg` (независимый декодер, включается автоматически при сбое soundfile), но при 0.12.1 он на текущих датасетах не задействуется.
- **Возобновляемость обязательна.** Прогоны на CPU длительные; стадия, прерванная на N%, при рестарте продолжает с невыполненного, а не с нуля (§7). Это требование не зависит от машины и полезно и на GPU.

**Текущий профиль машины (не аксиома архитектуры).** Разработка идёт на ноутбуке **без GPU, на CPU**, с бюджетом RAM **≤ 5 ГБ** (всего 7.7 ГБ). Это *свойство текущей машины*, а не встроенное в архитектуру допущение: `device` (`cpu`/`cuda`), `batch_size`, `num_workers` — **параметры конфига, а не константы в коде** (§3, §7). Возможный переезд на GPU-машину при этом не требует переписывания.

### Развёртывание окружения `[РЕШЕНО]`

Менеджер — **`uv`** в проектном режиме (`pyproject.toml` + `uv.lock`), не `uv pip` и не `requirements.txt`. Docker сознательно отвергнут: для одиночной исследовательской работы контейнер добавляет слой, который нужно объяснять, не улучшая ни одного критерия защиты.

**Установка с нуля** (Linux и Windows одинаково):

```bash
uv sync --extra cpu     # машина без NVIDIA GPU
uv sync --extra gpu     # машина с NVIDIA GPU (CUDA 13)
uv run python -m src.doctor
```

Отдельно ставить Python не нужно: `.python-version` задаёт 3.12, и `uv` скачает интерпретатор сам, если его нет в системе.

**Запуск стадий.** Все команды §4 работают с префиксом `uv run`, из корня проекта:
`uv run python -m src.data.manifest --list`, `uv run python -m src.train --config …` и так далее. Активировать `.venv` не нужно — `uv run` подхватывает окружение и досинхронизирует его по локфайлу перед запуском. Альтернатива для длинной сессии: один раз `source .venv/bin/activate` (`.venv\Scripts\activate` в Windows), дальше команды §4 без префикса.

**Почему `torch` в экстрах, а не выбирается автоматически.** Маркеры платформы в `pyproject.toml` различают ОС, но не наличие видеокарты, а нужны все четыре комбинации. По умолчанию PyPI отдаёт CPU-сборку на Windows и CUDA-сборку на Linux — то есть Windows + NVIDIA молча получил бы `torch` без CUDA. Флаг `--torch-backend=auto` умеет определять железо, но работает только в pip-интерфейсе `uv` (`uv pip install`), а не с `uv sync`/`uv lock`/`uv run`, — с локфайлом он несовместим. Поэтому выбор явный и заметный: экстры `cpu`/`gpu` с объявленным конфликтом в `[tool.uv] conflicts`; обе резолюции лежат в одном `uv.lock`. Цена ошибки нулевая — `src/doctor.py` печатает `torch.cuda.is_available()` и предупреждает, если стоит CUDA-сборка при невидимом GPU.

**Проект не устанавливается как пакет** (`[tool.uv] package = false`). Причина: у модулей относительные импорты (`from ..config import …`), то есть имя пакета — буквально `src`; упаковка ради упаковки потребовала бы трогать импорты во всех файлах. Следствие — правило §4 остаётся в силе: `python -m src.<модуль>` **строго из корня проекта**.

**Ноутбуки** (`jupyterlab`, `ipykernel`, `ipywidgets`) вынесены в группу `dev` и ставятся по умолчанию. `jupyterlab` включён намеренно: развёртывание не должно предполагать конкретный редактор — `uv run jupyter lab` даёт самодостаточную среду, а `ipykernel` обслуживает и внешних клиентов (VS Code), поскольку это ядро, а не интерфейс. Голое окружение прогона без всего этого: `uv sync --no-dev --extra cpu`.

**Правки зависимостей.** Новая библиотека — `uv add <pkg>` (сам правит `pyproject.toml` и `uv.lock`); после ручной правки `pyproject.toml` — `uv lock`. `uv.lock` **коммитится всегда**: это и есть фиксация среды для критерия №2, вместе с `_spec.json` в кэше признаков (§6.5). Нижние границы версий выставлены по реально прогонявшейся конфигурации: апгрейд разрешён, даунгрейд ниже проверенного — нет.

**`soundfile` — единственный точный пин** (`==0.12.1`), обоснование выше в этом же §2. `uv add -U soundfile` вернёт баг libsndfile 1.2.2; `doctor` ловит это отдельной проверкой версии libsndfile, потому что иначе баг виден только по `_failures.csv` через час прогона.

**Запасной путь без `uv`:** `uv export --extra cpu --no-hashes -o requirements.txt`. Такой `requirements.txt` — **производный артефакт**, источник истины — `pyproject.toml` + `uv.lock`. Прежний `requirements.txt` (дамп `pip freeze` с колёсами `nvidia-*`, привязанный к Linux + CUDA 13) заменён и не поддерживается.

**Не-Python зависимости:** только `ffmpeg`, и тот опционален — фолбэк декодирования (§2), на текущих датасетах при `soundfile 0.12.1` не задействуется. Больше системных требований нет.

**Данные в развёртывание не входят.** `data/raw/` в git не хранится (§5); ожидаемое расположение — `data/raw/<dataset_id>/` с нетронутой родной структурой. Список `dataset_id` — `uv run python -m src.data.manifest --list`, источники и особенности каждого — Приложение А. Что реально лежит на диске, показывает `uv run python -m src.doctor` (каталоги не обходятся целиком: у наборов 2021 сотни тысяч файлов, полный `glob` был бы дороже самой проверки).

## 3. Архитектурная философия (почему всё устроено именно так)

**Принцип, не зависящий от машины:** пиковое потребление памяти должно зависеть от **размера батча, а не от размера датасета.** Это верно для любой конечной памяти — RAM на CPU сейчас, VRAM на GPU потом.

Отсюда — **долговечное ядро** (полезно на любом железе и обслуживает критерий №2):

1. **Стадийность с кэшем на диск.** Обработка разнесена на независимые стадии; промежуточные результаты лежат на диске, в памяти держится только текущая порция.
2. **Признаки считаются один раз и кэшируются.** Извлечение признаков — самый дорогой шаг на CPU; платится один раз, дальше эксперименты читают готовый кэш. Кэш ещё и **переносим между машинами**.
3. **Возобновляемость (resumability).** Длинная стадия при перезапуске пропускает уже сделанное (§7).
4. **Развязанность = сравнимость экспериментов.** Смена «направления» — замена одного модуля (признаки или модель) без переписывания остального. Каждая стадия логируется отдельно → измеримость.
5. **Агностичность по трём осям `[РЕШЕНО как требование]`.** Датасеты, признаки и модели подбираются экспериментально → система не «знает» заранее конкретный датасет/признак/модель. Стабильные интерфейсы между сменными частями: **манифест** (любой датасет → пайплайн, §6.1), **кэш признаков** (любые признаки → обучение, §6.5) и **контракт признак↔модель** (любые признаки → любая модель, §6.6).
   - **Правило не-ветвления (простое операциональное определение).** Ниже манифеста стадии читают только канонические колонки (§6.1). Единственные законные употребления `dataset_id` — `concat` (склейка манифестов) и `group-by` (стратификация/разбивка). Появление `if dataset_id == …` ниже манифеста — **code smell**: чинить надо схему, а не вставлять частный случай. Всё датасет-специфичное живёт **только** в адаптере `sources/` (§6.2).
   - **Глобальный ключ примера — пара (`dataset_id`, `utt_id`).** Имена файлов между датасетами могут совпадать, поэтому `utt_id` глобально не уникален. Пара уникальна и служит ключом кэша признаков и ключом «пропустить готовое» (§7).
6. **Портируемость.** Устройство и размеры батча/воркеров — параметры (§2, §7); цикл обучения делает `tensor.to(device)`, а не хардкодит `.cpu()`. Никакой «мультидевайсной абстракции» не строится — это было бы переусложнением; достаточно не вписывать «CPU» в код как факт.

### Текущий профиль памяти (потолок 5 ГБ) — где реально риск
Это раздел про *текущую машину*, не про архитектуру. Из 5 ГБ часть уже занимает базовый процесс: импорт `torch`/`numpy`/`librosa` резидентно — обычно сотни МБ (*оценка, не точный факт — стоит измерить через `psutil`*). Реальный бюджет под данные/модель ≈ 3.5–4 ГБ. Риск OOM концентрируется **не** в стадии 1:
- **Стадия 1 безопасна по RAM.** Один аудиофайл во `float32` — единицы–десятки МБ (5 мин при 16 кГц ≈ 18 МБ). Стадия 1 ограничена временем CPU и местом на диске, а не памятью.
- **Реальные источники OOM:** (а) случайная материализация всего датасета/матрицы признаков в один массив/`DataFrame`; (б) `DataLoader` с несколькими воркерами — каждый процесс дублирует память; (в) большой батч / удержание графа в обучении; (г) **загрузка тяжёлой модели**: SSL вроде wav2vec2/HuBERT ≈ 300M параметров ≈ **1.2 ГБ только веса** = четверть бюджета, и медленно на CPU → на текущей машине SSL-направление маргинально (учитывать при выборе направления; на GPU это ограничение снимается, но см. дисциплинарный риск в §1).

### Запуск Стадии 0 `[РЕШЕНО]`

Стадия 0 запускается **как модуль пакета** (`python -m …`), а не как файл: в
`manifest.py` относительные импорты (`from ..config …`), поэтому `python
src/data/manifest.py` сломается — правильно только `python -m src.data.manifest`.
Команду выполнять **из корня проекта** (папка, где лежит `src/`). Это *тонкий
раннер одной стадии*, а не глобальный `main.py`/диспетчер (последний §4 сознательно
отвергает); у каждой стадии свой запуск через `-m`.

```bash
# один датасет
python -m src.data.manifest for-2seconds

# несколько сразу
python -m src.data.manifest asvspoof2019_la asvspoof2021_la asvspoof2021_df

# все зарегистрированные адаптеры
python -m src.data.manifest --all

# показать доступные dataset_id и выйти
python -m src.data.manifest --list
```

**Флаги:**

| Аргумент | Назначение |
|---|---|
| `datasets` (позиционные) | один или несколько `dataset_id` (= имена папок в `data/raw/`, совпадают с выводом `--list`) |
| `--all` | обработать все зарегистрированные адаптеры |
| `--list` | показать доступные `dataset_id` и выйти |
| `--root PATH` | задать корень проекта вручную (по умолчанию определяется от расположения `src/config.py`; нужен только при запуске из нестандартного места или на другом дереве данных) |

**Что делает.** Для каждого датасета: адаптер → валидатор (§6.1) → атомарная
запись `data/manifests/<dataset_id>.parquet` → атомарная запись паспорта
`data/manifests/<dataset_id>.manifest.json` (§6.5); печатает сводку (число строк,
баланс классов по сплитам, заполненность опциональных колонок) — это сразу
санити-проверка. Каталог `data/manifests/` создаётся автоматически.

**Поведение при ошибке.** Один датасет — исключение пробрасывается с понятным
сообщением. Несколько / `--all` — раннер не падает на первом сбое: печатает
`[<ds>] ОШИБКА: …`, продолжает остальные и в конце возвращает код `1` со списком
не удавшихся. Так один битый датасет не прячет успех прочих.

**Тонкости и порядок прогона.**
- Первый прогон делать **по одному датасету** — чтобы изолировать возможный сбой (внешние ключи 2021, наличие меток в eval-протоколе 2019 и т.п.).
- 2021 LA/DF — сотни тысяч файлов: `glob` по папке занимает заметное время, но **аудио не читается** (только пути/метаданные, §4), память не растёт.
- DF даёт **меньше** строк полного eval — это индексируется часть `part00` (Приложение А), так и отчитывается в работе.
- 2019 LA индексируется **по CM-протоколу**; ASV-enrollment из папок `dev/eval` flac (файлы вида `LA_D_A…`) в манифест не входит.

### Сборка `mini` — не стадия `[РЕШЕНО, v15]`

Крошечный датасет для smoke-прогонов (§6.4). Собирается **из уже построенных
манифестов**: по 5 подлинных + 5 спуф записей с каждого источника, аудио копируется
в `data/raw/mini/<источник>/`, рядом пишется `_index.csv` — «родной протокол»
получившейся папки. Дальше `mini` индексируется обычной Стадией 0 и ничем не
отличается от любого другого датасета (§3).

```bash
python -m src.data.mini                  # из всех датасетов с готовым манифестом
python -m src.data.mini asvspoof2019_la  # только из указанных источников
python -m src.data.mini --force          # удалить data/raw/mini/ и собрать заново
python -m src.data.manifest mini         # затем обычная Стадия 0
```

**Почему отдельная команда, а не адаптер.** Адаптер по контракту (§6.2) только
читает `data/raw/<ds>/` и аудио не грузит. Здесь же надо копировать файлы и читать
**чужие** манифесты. Разделение сохраняет контракт: генератор материализует папку,
адаптер (`sources/mini.py`) её индексирует.

**Почему 5+5, а не «первые 10».** Оба класса обязаны быть в каждом сплите:
`compute_eer` на одноклассовой выборке возвращает NaN (§8), а `pos_weight`
отключается. Прогон при этом формально не падает, но числовой путь «скор → метка →
EER» остаётся непроверенным — а это самое ценное в smoke-тесте. Разделимость
классов при этом **не** подразумевается: записи берутся как есть.

**Раскладка по сплитам:** с каждого источника 4 train / 4 dev / 2 test (по 2+2 / 2+2
/ 1+1 на класс). Источник, у которого меньше 5 записей какого-то класса,
пропускается с явной причиной, сборка не падает.

> ⚠️ **Числа с `mini` в работу не идут.** Записи берутся из всех сплитов источников
> и переразмечаются заново, то есть утечка между `train` и `test` заведомо есть, а на
> двух тестовых примерах EER не определён содержательно. Это инструмент проверки
> кода, а не измерения (§6.4).

### Запуск Стадии 1 `[РЕШЕНО]`

Как и Стадия 0 — **модуль пакета** (`python -m src.data.features`), из корня
проекта, относительные импорты (`python src/data/features.py` сломается). Тонкий
раннер одной стадии, не глобальный диспетчер (§4). У Стадии 1 две оси: датасет(ы)
и **один экстрактор за прогон** (одна конфигурация признаков = одна папка кэша).

```bash
# один датасет, один экстрактор
python -m src.data.features asvspoof2019_la -f lfcc

# несколько датасетов сразу (экстрактор один на прогон)
python -m src.data.features asvspoof2021_la asvspoof2021_df -f lfcc

# все датасеты, у которых уже построен манифест
python -m src.data.features --all -f logmel

# показать экстракторы и доступные датасеты, выйти
python -m src.data.features --list

# быстрый smoke-тест на первых N примерах
python -m src.data.features for-2seconds -f lfcc --limit 200
```

**Флаги:**

| Аргумент | Назначение |
|---|---|
| `datasets` (позиционные) | один/несколько `dataset_id`; манифест датасета должен существовать |
| `-f`, `--features NAME` | какой экстрактор (список — в `--list`); один на прогон |
| `--all` | все датасеты с готовым манифестом в `data/manifests/` |
| `--list` | показать экстракторы (с `C`/`sr`/хэшем) и доступные датасеты, выйти |
| `--limit N` | только первые N (стабильно отсортированных) примеров — smoke-тест, **не** для итоговых метрик |
| `--root PATH` | корень проекта вручную (по умолчанию — автоопределение от `src/config.py`) |

**Экстракторы (на данный момент).** `lfcc` (C=60, LFCC-60: 20 коэф. × static/Δ/ΔΔ),
`logmel` (C=80). Новый признак = новый класс + `@register_extractor`, ничего ниже
не трогая (реестр — зеркало `sources/`).

**Что делает.** Для каждого датасета читает `data/manifests/<dataset_id>.parquet`
(только метаданные — память не зависит от размера аудио), стабильно сортирует по
(`dataset_id`, `utt_id`), файл за файлом: путь выхода детерминирован → есть →
пропуск; иначе декодирует аудио → извлекает `[T, C]` → проверяет контракт (§6.6) →
**атомарно** пишет `.npy`. Раскладка кэша:
`data/features/<name>-<hash>/<dataset_id>/<utt_id>.npy`, где `hash` = sha1 конфига
признаков. Пишет паспорт папки `_spec.json` (параметры + версии библиотек) и, при
сбоях, `<dataset_id>/_failures.csv` (сбойный файл + реальная причина). Печатает
сводку (всего / записано / пропущено / ошибок).

**Предусловие.** Манифест обязан быть построен (Стадия 0). Нет манифеста → понятная
ошибка с подсказкой запустить Стадию 0.

**Возобновляемость.** «Пропустить готовое» + атомарная запись (§7): прерванный
прогон продолжается с невыполненного. Рабочий цикл: `--limit` (быстро) → полный
манифест, который пропускает уже посчитанное.

**Поведение при ошибке.** Единичный битый/недекодируемый файл логируется в
`_failures.csv` и **не** роняет прогон. Систематический сбой (0 успехов на непустом
входе) или отсутствие манифеста помечает датасет как неудавшийся. Несколько
датасетов — раннер не падает на первом: печатает `[<ds>] ОШИБКА: …`, продолжает и в
конце возвращает код `1` со списком не удавшихся (как в Стадии 0).

**Тонкости.**
- Разные параметры экстрактора → разный `hash` → разные папки кэша, наборы не путаются; возврат к прежним параметрам не вызывает пересчёта.
- `logmel` считать только когда понадобится — иначе зря занятые ГБ на диске.
- Декодирование: soundfile (быстрый путь) с автоматическим фолбэком на ffmpeg при сбое (§2); при `soundfile==0.12.1` фолбэк на текущих датасетах не нужен.
- Итоговый EER берётся на **полном** тесте, не на `--limit`-срезе (§6.4).

### Запуск Стадии 2 `[РЕШЕНО]`

Как Стадии 0/1 — **модуль пакета** (`python -m src.train`), из корня проекта
(относительные импорты; `python src/train.py` сломается). Тонкий раннер одной
стадии, не глобальный диспетчер (§4). Прогон описывается **одним YAML-конфигом**
`experiments/<exp>.yaml`; `config.py` остаётся статикой (пути, seed, дефолты
среды), YAML переопределяет их секцией `runtime` (§2, §3).

```bash
# показать зарегистрированные признаки и модели, выйти
python -m src.train --list

# запустить прогон по конфигу
python -m src.train --config experiments/lfcc_statpool.yaml
```

**Флаги:**

| Аргумент | Назначение |
|---|---|
| `--config PATH` | `experiments/<exp>.yaml` — полное описание прогона (обязателен, кроме `--list`) |
| `--list` | показать доступные признаки/модели и выйти |
| `--root PATH` | корень проекта вручную (по умолчанию — автоопределение от `src/config.py`) |

**Структура конфига** (примеры — `experiments/lfcc_statpool.yaml` для полного прогона,
`experiments/smoke_mini.yaml` для smoke):
`name` (→ папка артефактов `experiments/<name>/`), `feature.name` (только имя из
реестра — параметров здесь нет, §6.6), `model.{name, params}`, `data.{train, val, t_fixed}`,
`train.{epochs, lr, weight_decay, pos_weight, ckpt_every, keep_last}`, `runtime.*`.
`train`/`val` — списки селекторов `{dataset_id, split}`; при нескольких датасетах
манифесты склеиваются (§3). **Объём прогона задаётся только этими списками** (§6.4):
секции подвыборки нет — быстрый прогон делается на маленьком датасете (`mini`), а не
на срезе большого.

**Что делает.** Резолвит признак → его `C` и папку кэша; **pre-flight** сверяет
`C` кэша (из `_spec.json`) с `C`, который объявляет модель (§6.6) — рассинхрон
«признак ≠ модель» и отсутствие кэша ловятся **до** обучения, с понятной ошибкой и
подсказкой про Стадию 1. Читает манифесты по селекторам (стабильно отсортированными,
§6.4), лениво грузит признаки (в памяти только батч, §3/§7), учит; в конце каждой эпохи считает
val-EER (общая утилита `utils/metrics`, §8), пишет строку в `metrics.jsonl` и
чекпойнт. Печатает по эпохам loss и val-EER.

**Артефакты** — в `experiments/<name>/` (§6.5): `metrics.jsonl` (эпоха, loss,
val-EER, порог, lr), `ckpt_epoch*.pt` (последние `keep_last`), `best.pt` (мин.
val-EER), `final.pt` (последняя эпоха).

**Предусловия.** (1) Манифест датасета(ов) построен (Стадия 0). (2) Кэш признака
покрывает нужные примеры. **Полный прогон Стадии 1 не требуется** — Стадия 2 читает
`.npy` по ключу (`dataset_id`, `utt_id`) и отфильтровывает отсутствующие с
предупреждением, т.е. работает по фактически посчитанному кэшу. После удаления
подвыборок (§6.4, v15) это стало и рабочим приёмом: `features <ds> -f lfcc --limit N`
считает первые N после стабильной сортировки, и обучение честно идёт ровно по ним.
На Стадии 3 такой прогон упрётся в `min_coverage` — и правильно: оценка по части
теста не должна проходить молча.

**Возобновляемость (§7).** Прерванный прогон при перезапуске **той же командой**
подхватывает последний чекпойнт (модель + оптимизатор + эпоха), продолжает с
невыполненной эпохи; `metrics.jsonl` дедуплицируется по эпохе. Ротация держит
последние `keep_last` чекпойнтов (клампится к ≥ 1 — без чекпойнта нет resume).

**Smoke-first (§6.4).** Основной режим разработки — прогон на датасете `mini`
(`experiments/smoke_mini.yaml`): за минуты видно, что цикл, чекпойнты, лог и val-EER
живы. Полные прогоны отложены до завершения проекта; итоговый EER — на полном тесте
(§6.4).

### Запуск Стадии 3 `[РЕШЕНО]`

Как Стадии 0/1/2 — **модуль пакета** (`python -m src.evaluate`), из корня проекта.
Конфиг — **тот же самый** `experiments/<exp>.yaml`, что у обучения `[РЕШЕНО]`:
признак и архитектура тогда заведомо одни и те же, рассинхрон «оценили не тем, чем
учили» невозможен по построению. Стадия 3 читает секции `data.test` и `eval.*`;
Стадия 2 их игнорирует.

```bash
# оценка по конфигу (веса — из eval.weights, по умолчанию best.pt)
python -m src.evaluate --config experiments/lfcc_statpool.yaml

# явно выбрать веса
python -m src.evaluate --config experiments/<exp>.yaml --weights final
python -m src.evaluate --config experiments/<exp>.yaml --weights experiments/<exp>/ckpt_epoch0007.pt

# посчитать при неполном кэше признаков (осознанно)
python -m src.evaluate --config experiments/<exp>.yaml --allow-missing
```

**Флаги:**

| Аргумент | Назначение |
|---|---|
| `--config PATH` | `experiments/<exp>.yaml` — тот же файл, что у Стадии 2 (обязателен, кроме `--list`) |
| `--weights` | `best` \| `final` \| путь к `.pt`; переопределяет `eval.weights` |
| `--allow-missing` | не падать при покрытии ниже `eval.min_coverage` |
| `--list` | показать доступные признаки/модели и выйти |
| `--root PATH` | корень проекта вручную |

**Секция `eval` конфига:** `weights` (best/final/путь), `window` (`fixed`; `full`/`sliding`
— `[НЕ НАЧАТО]`, §9), `bootstrap` (число повторов CI; 0 — выключить), `bootstrap_seed`,
`ci` (уровень, дефолт 0.95), `min_coverage` (дефолт 0.99), `shard_rows` (строк на шард).

**Что делает.** Резолвит веса → восстанавливает модель **по метаданным чекпойнта**
(`model_name`, `model_params`, `in_channels`, `t_fixed`), а не по YAML: так оценка идёт
той же архитектурой и с тем же входом, что были при обучении. **Pre-flight строже, чем
на Стадии 2** (§6.6): помимо `C` кэша сверяется `feature_hash` из чекпойнта — ловится
случай «C совпал, а параметры признака другие», который одной сверкой `C` не отличить.
Дальше: читает тестовые манифесты по селекторам (склейка, §3), лениво прогоняет
модель по кэшу, пишет скоры и считает метрики.

**Метрики — по каждому датасету отдельно** `[РЕШЕНО]`. Общего EER по смеси датасетов
нет намеренно: он смешал бы разные домены и разные классовые пропорции в одно
неинтерпретируемое число. Кросс-датасетный вывод (§8) читается сравнением строк.

**Артефакты** — в `experiments/<name>/` (§6.5): `scores.parquet` (выгрузка скоров),
`eval_metrics.json` (EER + бутстрэп-CI, матрицы ошибок на двух порогах, разбивка EER
по атакам, покрытие, паспорт чекпойнта).

**Предусловия.** (1) Прогнана Стадия 2 — есть `best.pt`/`final.pt`. (2) Кэш признака
покрывает тестовые примеры. Неполное покрытие меняет знаменатель метрики, поэтому оно
не замалчивается: доля пишется в `eval_metrics.json`, а падение ниже `min_coverage`
роняет прогон (обойти — `--allow-missing`, честно оговорив покрытие в работе).

**Возобновляемость (§7).** Скоры пишутся шардами в `experiments/<name>/scores_parts/`;
при рестарте **той же командой** уже посчитанные ключи (`dataset_id`, `utt_id`)
пропускаются, в конце шарды склеиваются в `scores.parquet` и удаляются. Рядом лежит
**отпечаток условий** прогона (веса, эпоха, `feature_hash`, `t_fixed`, окно,
селекторы): изменились условия — прежние шарды удаляются с предупреждением, а не
смешиваются с новыми.

**Тонкости.**
- `t_fixed` берётся **из чекпойнта**, не из YAML: менять его между обучением и оценкой означало бы оценивать модель на входе другой длины.
- Окно на тесте — детерминированное, с начала записи, как на валидации Стадии 2 (§7). Это осознанный выбор ради сопоставимости; следствия для коротких датасетов — см. §8.
- Скор = **сырой логит**, больше ⇒ спуф. В официальных протоколах ASVspoof знак обратный (§8).

## 6. Контракт данных и артефактов `[РЕШЕНО]`

Ноутбуки и `viz`-модули **ничего не пересчитывают** — они читают готовые артефакты с диска. Стадии обязаны эти артефакты писать. Но прежде артефактов — **контракт данных**: при открытом множестве датасетов объект проектирования не «ASVspoof и FoR», а *схема и правила, которым обязан удовлетворять любой будущий датасет*. ASVspoof/FoR ниже фигурируют только как два крайних случая (протокол с метаданными / ничего, кроме имён папок), на которых контракт проверяется на прочность.

### 6.1 Каноническая схема манифеста `[РЕШЕНО]`
Манифест — **единственный** универсальный интерфейс «любой датасет → пайплайн». Любой адаптер обязан выдавать ровно эту схему; всё ниже манифеста полагается только на неё (правило не-ветвления, §3).

**Обязательные колонки:**
- `dataset_id` (str) — происхождение, напр. `asvspoof2019_la`. Нужна для безопасного склеивания манифестов (`concat`) при кросс-датасетных экспериментах и как часть глобального ключа.
- `utt_id` (str) — уникален **внутри** датасета. Пара (`dataset_id`, `utt_id`) глобально уникальна → ключ кэша признаков и ключ «пропустить готовое».
- `path` (str) — путь к аудио относительно `raw/<dataset_id>/`.
- `label` (int) — **фиксированная конвенция, одна для всех адаптеров: `spoof = 1`, `bonafide = 0`** (положительный класс = детектируемая синтетика). Это *решение*, а не факт, — но оно единое и записано.
- `split` (str) ∈ `{train, dev, test}` — нормализованный (см. 6.3).

**Опциональные колонки (NULL при отсутствии):**
- `attack_type` (str) — напр. `A01…` у датасетов с протоколом; NULL там, где разметки атак нет.
- `condition` (str) — кодек/сжатие, применённые к **сигналу** до сохранения (`low_mp3`, `nocodec` у DF-2021; `g722`, `none` у LA-2021). Ось разбивки EER по условиям (§8).
- `transmission` (str) — канал передачи (LA-2021: `loc_tx`/`sin_tx`/`ita_tx`/`mad_tx`). Отдельная колонка, а не склейка с `condition`: одно поле — один факт, разбивку по паре даёт `groupby` обеих, а разбор склеенной строки обратно был бы парсингом.
- `vocoder` (str) — вокодер спуф-системы, где размечен (DF-2021).
- `speaker_id` (str) — NULL, если датасет дикторов не размечает.
- `sample_rate` (int), `codec` (str: flac/wav/…), `duration` (float, сек).

> **Ловушка имён (v14).** `codec` — формат **контейнера файла на диске** (везде в текущих наборах `flac`), выводится из расширения. `condition` — кодек, применённый к **самому сигналу**. Строка манифеста вида `codec=flac, condition=low_mp3` не противоречива: сигнал прогнали через mp3 и разжали обратно, а на диске он лежит как FLAC. Переименование `codec → container` обсуждалось и **отклонено** (решение пользователя); различие держится документацией, а не именем.

> **Локальность значений.** `attack_type`, `condition`, `transmission`, `vocoder` — **локальные для датасета** словари. Группировать по ним допустимо только внутри одного `dataset_id`. `condition="none"` у LA-2021 и `condition="nocodec"` у DF-2021 означают одно и то же по смыслу, но нормализовать их к общему токену намеренно **не** делается: гармонизация словарей между датасетами — это уже интерпретация, а манифест обязан оставаться точной записью того, что размечено в источнике. Отдельно: NULL в `condition` (у 2019 LA и FoR условий нет в принципе) — **не** то же, что `"none"`/`"nocodec"` (условие есть, сжатие не применялось); смешивать их в одну группу нельзя.

**Правило отсутствующих полей:** явный **NULL** (pandas NA), **не** магическая строка (`"unknown"`). Причина — отличать «поля нет в датасете» от «поле есть, но значение неизвестно». Потребители (напр. разбивка EER по атакам, §8) обязаны **пропускать** строки с NULL в `attack_type`, а не считать NULL отдельной «атакой».

> **Уточнение к правилу (внесено на Стадии 3, v12).** Правило относится к **спуф-строкам** с неизвестной атакой. У подлинных записей `attack_type` **всегда** NULL по конвенции, и они обязаны участвовать в разбивке как отрицательный класс: EER для атаки `A07` — это «весь bonafide датасета против спуфа только этой атаки». Буквальное чтение «пропускать все строки с NULL» оставило бы разбивку без отрицательного класса, и EER стал бы неопределён. Реализовано в `evaluate._eer_by_attack`; число пропущенных спуф-строк без атаки пишется в `eval_metrics.json` (`n_spoof_without_attack_type`), чтобы пропуск был виден, а не молчалив.

> **Почему это критерий №2.** Схема + функция-валидатор (`schema.py`), через которую проходит выход *любого* адаптера (обязательные колонки, типы, `label ∈ {0,1}`, `split ∈ {train,dev,test}`, уникальность ключа, отсутствие сентинелов в `attack_type`), превращают агностичность из лозунга в **проверяемый контракт** — измеримый вклад.

> **Инварианты имён (добавлено v14).** Валидатор проверяет ещё две вещи, которые раньше были неявным договором между Стадиями 0 и 1: `utt_id` матчится `^[A-Za-z0-9._-]+$` и не равен `.`/`..`; `path` — относительный posix-путь без `..` и без ведущего `/`. Основание: `utt_id` становится **именем файла** в кэше признаков (`features/<hash>/<dataset_id>/<utt_id>.npy`, §6.5), поэтому разделитель пути внутри него разложил бы кэш не туда, причём молча. Это ровно та категория, ради которой заведено правило «ошибки конфигурации ловятся до долгой работы» (§7).

### 6.2 Контракт адаптера (`sources/*`) `[РЕШЕНО]`
Адаптер инкапсулирует **всё** датасет-специфичное. Обязанности: (1) найти аудио в своём `raw/<dataset_id>/`; (2) разрешить **метку** на файл (источник — дело адаптера: протокол / имя папки / шаблон имени); (3) разрешить **родной сплит** либо пометить его отсутствие (§6.3); (4) заполнить опциональные поля где есть, поставить **NULL** где нет. Выход обязан **проходить валидатор**. Наружу торчит только каноническая схема — обратная сторона правила не-ветвления (§3).

**Общее против специфичного (v14).** Разбор пробел-разделённых протоколов вынесен в `sources/common.py::protocol_table(path, fields={имя: индекс}, …)`: помощник читает файл, проверяет ширину строки и уникальность ключа, но **не знает семантики полей** — какое поле что значит и где лежит файл ключей остаётся в адаптере. Граница проведена именно здесь намеренно: словарь «имя → индекс» позволяет добавить новое поле (условие, вокодер) правкой одного адаптера, не трогая помощник. Более амбициозное обобщение — декларативное описание датасета в YAML вместо python-адаптера — рассмотрено и **отклонено**: любой датасет, не влезающий в схему описания (ключи вне папки датасета, частично скачанное аудио — оба случая уже есть), заставлял бы расширять DSL, и через несколько наборов это стало бы плохо отлаживаемым Python в конфиге. Цена текущего решения — один файл на ~60 строк на датасет — ниже.

### 6.3 Сплиты: родной против назначенного `[РЕШЕНО, v14]`
Система **не предполагает** наличия родного деления — датасет может быть просто набором файлов. Источник сплита бывает двух видов, адаптер обязан их различать:
- **родной сплит** — адаптер читает его из датасета (протокол или структура папок) и нормализует в `{train, dev, test}` (напр. `eval → test`; `validation → dev`);
- **назначенный сплит** — датасет деления не имеет → сплит присваивает **проект** по явной политике-параметру.

**Политика назначения (предпочтение):** деление **по диктору** — чтобы записи одного диктора не попадали и в `train`, и в `test` (утечка диктора, §8). Возможно только при наличии `speaker_id`; иначе деградация до **случайного с seed** + **явная пометка об ограничении**.

> **Решение по объёму работы (v14).** В работу берутся **только датасеты с авторским делением**. Назначаемый сплит не реализуется: ни один из четырёх наборов его не требует, а введение собственной политики деления сделало бы *дизайн сплита* ещё одной переменной, влияющей на сравнение EER между наборами. Формулировка для защиты: деление данных вынесено за пределы ответственности работы и берётся у авторов датасетов.
>
> **Кода не требуется — это уже обеспечено контрактом.** Валидатор требует `split ∈ {train, dev, test}` без NULL (§6.1), поэтому адаптер для набора без деления физически не может отдать манифест, не приняв решение о сплите явно. Пути «поделилось само, молча» в системе нет.
>
> **Граница решения.** Брать авторское деление — значит довериться тому, как оно спроектировано. У ASVspoof это сильная сторона (train и eval построены на непересекающихся атаках). Про FoR неизвестно, разведены ли дикторы между `training` и `testing`, и это **не проверялось**: в текущей схеме обучение идёт только на 2019 LA, а FoR используется как тестовый набор, поэтому утечка через его внутреннее деление невозможна. Манифест FoR при этом содержит все три сплита — если когда-нибудь `data.train` в конфиге эксперимента затянет `for-2seconds`, вопрос про разведение дикторов придётся задать заново. Обратно к назначаемым сплитам возвращаться дёшево: помощник на группировку по хэшу `speaker_id` — порядка 30 строк в `sources/common.py`.

### 6.4 Объём прогона `[РЕШЕНО, v15]`

**Единственная ручка — состав селекторов.** Сколько данных увидит прогон, определяют
списки `data.train` / `data.val` / `data.test` в `experiments/<exp>.yaml`: какие
датасеты, какие сплиты. Никакого второго механизма «взять N строк» нет.

**Подвыборки — `[ОТКЛОНЕНО, v15]`.** До v15 существовал `src/data/subsets.py`:
детерминированная стратифицированная выборка `n` строк манифеста с зафиксированным
seed, плюс секция `data.subset` в конфиге. Механизм работал, но тянул за собой
стратификацию (и её автодополнение `dataset_id` при склейке), seed, отдельный
артефакт `manifests/subsets/*.parquet`, лишние поля в отпечатке шардов Стадии 3 и —
главное — постоянную заботу о том, чтобы кэш Стадии 1 покрывал именно ту выборку,
которую возьмут Стадии 2–3. Ради единственного реального сценария («убедиться, что
код отрабатывает целиком») это дорого. Решение: механизм удалён, сценарий закрыт
маленьким датасетом.

*Что осталось от него по существу.* Инвариант «**стабильная сортировка по
(`dataset_id`, `utt_id`)** перед всем остальным» жил в `make_subset`, который
вызывался всегда — даже когда выборка не бралась. Он перенесён в
`selectors.load_selectors`, потому что порядок строк определяет порядок примеров в
`Dataset`, а на Стадии 3 — соответствие «скор ↔ ключ» (§7). Без переноса удаление
подвыборок сломало бы корректность молча.

**Маленький прогон = маленький датасет `mini` `[РЕШЕНО, v15]`.** `python -m
src.data.mini` собирает `data/raw/mini/` из уже построенных манифестов: по 5
подлинных + 5 спуф записей с каждого источника, разложенных 4 train / 4 dev / 2 test.
Дальше — обычные Стадии 0–3 (`experiments/smoke_mini.yaml`). Подробности запуска и
обоснование пропорции 5+5 — в §4. Ключевое отличие от подвыборки: это **отдельный
`dataset_id`**, а не срез существующего, поэтому у него свой манифест, свой кэш
признаков и никакой синхронизации ни с чем не требуется.

> ⚠️ **`mini` не измеряет.** Записи взяты из всех сплитов источников и переразмечены
> заново — утечка между `train` и `test` заведомо есть. Датасет проверяет, что код
> работает, а не насколько хорош метод.

**Быстрый прогон на большом датасете** (когда нужен именно реальный домен) делается
флагом Стадии 1 `--limit N`: считаются первые N примеров после стабильной сортировки,
а Стадия 2 отфильтровывает отсутствующие в кэше строки с предупреждением и учится
ровно по посчитанному. Стадия 3 в этом режиме упрётся в `min_coverage` — это
намеренно (§4).

**Оговорка (важно для критерия №2).** Итоговый EER берётся на **полном** тесте: на
малом тесте оценка EER имеет высокую дисперсию, а порог определён плохо. К итоговым
числам прикладываются **бутстрэп-доверительные интервалы** — *реализовано на Стадии 3
(`utils/metrics.bootstrap_eer`, стратификация по классу; §8)*. *(Бутстрэп-CI для EER —
стандартная практика в биометрии; точную ссылку перепроверить перед внесением в
текст.)*

### 6.5 Прочие артефакты `[РЕШЕНО]`
- **Паспорт манифеста** (`data/manifests/<dataset_id>.manifest.json`) `[РЕШЕНО, v14]`: сводка состава + провенанс, пишется Стадией 0 рядом с самим `.parquet`. Блоки: `manifest` (число строк, размер, **отпечаток** содержимого), `class_balance` (bonafide/spoof по сплитам), `columns` (заполненность каждой опциональной колонки + словарь значений для колонок мощностью ≤64), `adapter` (класс и модуль), `provenance` (версии python/pandas, git-коммит и «грязное ли дерево»).
  - **Зачем.** Две вещи, которых `.parquet` про себя не сообщает. Первая — числа состава данных идут прямо в текст работы (критерий №2), а раньше печатались в stdout и умирали вместе с терминалом. Вторая — «каким кодом собран этот файл»: без git-коммита пересборка после правки адаптера неотличима от исходной.
  - **Перезаписывается** при каждой пересборке — в отличие от `_spec.json` Стадии 1, который пишется один раз. Разница по существу: `_spec.json` описывает папку, накапливаемую многими прогонами, и обязан помнить, каким прогоном что посчитано; манифест же каждый раз строится целиком заново и должен описывать ровно текущий файл.
  - **Отпечаток** — sha1 стабильно отсортированного кадра в CSV-сериализации; не зависит от порядка обхода файлов адаптером. Сравним **в пределах одной среды**: смена версии pandas может изменить представление NULL и дать другой отпечаток при том же содержимом. Для вопроса «манифест изменился с прошлого прогона» этого достаточно; как канонический хэш датасета использовать нельзя.
  - Сводка в stdout считается **из паспорта**, а не из кадра заново — иначе одни и те же числа считались бы двумя путями и могли разойтись (то же правило, по которому ноутбуки не пересчитывают, а читают артефакты, §6).
- **Кэш признаков** (`data/features/`): **per-file `.npy`** — по одному файлу на пример; ключ пути — **(`dataset_id`, `utt_id`) + хэш конфига признаков**, чтобы разные наборы признаков не путались и не было пересчёта при возврате. → читает `dataset.py` и ноутбук аудиопризнаков. Папка кэша **самоописательна**: `_spec.json` (конфиг признаков + версии библиотек — воспроизводимость) и, при сбоях, `<dataset_id>/_failures.csv` (сбойный файл + причина).
- **Лог метрик обучения** (`experiments/<exp>/metrics.jsonl`): построчно по эпохам — `epoch`, `train_loss`, `val_eer`, `val_threshold`, `lr` (append + **дедуп по эпохе при возобновлении**, §7). → читает ноутбук обучения.
- **Веса и чекпойнты обучения** (`experiments/<exp>/`): `ckpt_epoch*.pt` (модель + оптимизатор + эпоха; последние `keep_last`, для возобновления §7), `best.pt` (мин. val-EER), `final.pt` (последняя эпоха). **Стадия 3 по умолчанию грузит `best.pt`.** Оговорка: на малой/шумной val «лучшая эпоха» может оказаться удачей, а не улучшением (высокая дисперсия EER, §6.4) — на полном val это не проблема, на smoke интерпретировать осторожно.
  - **Чекпойнт самодостаточен `[РЕШЕНО, v12]`.** В `meta` лежат `model_name`, **`model_params`**, `feature`, `feature_hash`, `in_channels`, `t_fixed`. `model_params` добавлены не для красоты: без них `get_model(name, in_channels)` собрал бы сеть с **дефолтными** размерами, и `load_state_dict` упал бы при любом отличии от конфига обучения (напр. `hidden: 256` вместо 128). С ними Стадия 3 восстанавливает модель, не заглядывая в YAML, — веса и конфиг могут быть от разных прогонов.
- **Выгрузка скоров** (`experiments/<exp>/scores.parquet`) `[РЕШЕНО, v12]`: одна строка на оценённый пример, колонки **`dataset_id, utt_id, split, label, attack_type, score`**. `score` — **сырой логит**, больше ⇒ спуф (§6.1, §8); сигмоида не применяется, EER инвариантен к монотонному преобразованию. → читает ноутбук результатов и `viz/results.py`.
- **Метрики оценки** (`experiments/<exp>/eval_metrics.json`) `[РЕШЕНО, v12]`: паспорт прогона (веса, эпоха, `checkpoint.meta`, окно, конвенция скора, покрытие) + блок `per_dataset` — на каждый `dataset_id`: `eer`, `eer_threshold`, `eer_ci` (бутстрэп), матрицы ошибок `at_eer_threshold` / `at_val_threshold`, `by_attack`. Ноутбук эти числа **только рисует**, не пересчитывает (§6) — иначе число в таблице и число на графике могли бы разойтись.
- **Шарды скоров** (`experiments/<exp>/scores_parts/`) — временные, механизм возобновления Стадии 3 (§7); удаляются после успешной склейки.

### 6.6 Контракт признак↔модель `[РЕШЕНО]` (модули реализованы, Стадия 2)
Третий интерфейс агностичности. «Модель-агностичный цикл обучения» остаётся агностичным только пока форма того, что кладёт экстрактор, зафиксирована — иначе LFCC `[T, 60]`, F0 `[T, 1]` и SSL-эмбеддинг ломают произвольную модель.

- **Форма.** Каждый экстрактор отдаёт `float32`-массив **`[T, C]`** (`T` — кадры по времени, `C` — каналы/коэффициенты). 1D-признаки (напр. F0) — это `[T, 1]`. Кэш (§6.5) хранит ровно `[T, C]`.
- **Коллация.** `dataset.py` возвращает один пример `[T, C]`; коллатор собирает батч `[B, T_fixed, C]` + `lengths`. *На Стадии 2 длина фиксируется (`t_fixed`), поэтому маска тривиальна (все `T` равны), но `lengths` возвращается — интерфейс сохранён под будущую честную переменную длину без правки моделей.* Это единственное место, где сходятся корректность и память батча.
- **Объявление входа.** Модель из реестра `models/` объявляет ожидаемое `C` (`in_channels`); несовпадение с конфигом признаков — ошибка конфигурации, ловится **до** обучения (как валидатор схемы в §6.1). *Реализовано: pre-flight в `train.py` сверяет `C` кэша (из `_spec.json`) с `C` модели.* Пулинг/свёртка по `T` до фиксированной длины — **обязанность модели**, не кэша: кэш остаётся `[T, C]`, контракт стабилен.
  - **Pre-flight Стадии 3 строже `[v12]`.** Помимо `C` сверяется **`feature_hash`**, записанный в чекпойнт при обучении, с хэшем признака из текущего конфига. Это ловит случай «`C` совпал (60 = 60), а параметры признака другие» — рассинхрон, который одной сверкой `C` не отличить. На Стадии 2 такой проверки нет и быть не может: там сравнивать не с чем, обучение и есть источник хэша.
- **Одно имя признака = одна конфигурация = одна папка кэша `[РЕШЕНО, v15]`.** Параметры экстрактора задаются **только его дефолтами**; секции `feature.overrides` в конфиге Стадий 2–3 больше нет, а `get_extractor(name)` не принимает параметров. Другая настройка — это другой зарегистрированный экстрактор со своим именем (`lfcc_nodelta` и т.п., ~6 строк подкласса).
  - **Мотив — закрытый разрыв.** С `overrides` конфиг Стадий 2–3 мог описать конфигурацию признака, которую CLI Стадии 1 построить не умел (параметров он не принимал): указать на папку кэша, которую нечем наполнить. Вторая, более тихая часть разрыва — хэш считается от JSON словаря параметров, а frozen dataclass типы не приводит, поэтому `overrides: {fmin: 0}` (int) давал **другую** папку, чем дефолтное `fmin=0.0` (float), при семантически одинаковой настройке. *(Проверено прогоном: хэши `18d55bf0fa` и `66dbe5fc88`.)* Оба случая теперь непредставимы, а не «согласованы вручную».
  - **Побочная польза.** `--list` становится полным каталогом того, что вообще можно построить, а у каждой изученной конфигурации появляется имя для строки в таблице результатов.
  - **Асимметрия с `model.params` намеренная:** гиперпараметры модели не влияют на раскладку кэша на диске и целиком сохраняются в чекпойнте (`model_params`, §6.5), поэтому рассинхрону там взяться неоткуда.
- **Устройство.** Перенос на `device` — здесь: коллатор/цикл делает `.to(device)` над собранным батчем (§3, п.6). Это единственная точка, знающая про CPU/GPU.

**Модель как первая в реестре — НАПОЛНЕНИЕ, не выбор архитектуры (§1, §9).** `statpool_mlp` (`models/statpool.py`): покадровый Linear+ReLU → масочный statistics-pooling (mean+std) по времени → MLP → **один логит** на пример (spoof=1; `BCEWithLogitsLoss`). Лёгкая, C-агностичная, time-агностичная. Смысл Стадии 2 — не «правильная сеть», а замкнутый агностичный цикл; следующая архитектура добавляется рядом новым классом + `@register_model`, цикл не меняется.

## 7. Конвенции и правила гигиены `[РЕШЕНО]`

### Память
- **Никогда** не материализовать весь датасет/все признаки в один объект. Всегда потоково / лениво с диска.
- **Хранение — per-file `.npy`** (§6.5): грузится один маленький файл целиком, memmap/HDF5 не нужны. *(Оговорка: шардирование/HDF5 понадобились бы только при очень большом числе файлов или тесном диске. При текущих объёмах (≤30 ГБ данных, ~60 ГБ свободно) — **не требуется**; см. §9. Исключение — SSL-эмбеддинги, которые могут быть крупнее аудио: если дойдёт до их кэширования, прикинуть объём заранее.)*
- **`Dataset.__init__` держит только манифест** (метаданные), не данные — иначе каждый воркер `DataLoader` дублирует это в памяти. Воркеров мало (0–2). *(Реализовано: `dataset.py` хранит только id/метки как numpy-массивы, не `DataFrame`.)*
- **Маленький батч из-за памяти → накопление градиента** (gradient accumulation) для большего *эффективного* батча без роста памяти. *(Включать только при реальном упоре в размер батча — сейчас не реализовано, §9.)*
- **Контроль памяти:** лёгкое логирование RSS (`psutil`) на ключевых шагах, чтобы ловить рост заранее.
- **dtype:** признаки в `float32`, не `float64`. На CPU `float16` не ускоряет и плохо поддержан — оставаться в `float32`.
- **`DataLoader`:** `num_workers` подбирать осторожно — на CPU обучение и загрузка конкурируют за ядра. Значение — параметр конфига (§2).

### Фикс-длина входа и аугментация (Стадия 2) `[РЕШЕНО]`
Каждый пример приводится к общей `t_fixed` (кроп длинного / **повтор-паддинг**
короткого — повтор, а не нули, чтобы кадры оставались «настоящими»). Это собирает
батч в один тензор и держит память батча предсказуемой (§3). Кроп длинного файла:
- **обучение** — окно берётся **случайно** (лёгкая аугментация: за эпохи модель видит разные фрагменты длинных записей → лучше обобщение; доменный стандарт анти-спуфинга);
- **валидация/оценка** — окно **детерминированно** с начала.

Смещение берётся из torch-ГСЧ, который `DataLoader` сеет по воркерам и эпохам →
прогон **воспроизводим от общего seed** (проверено: два прогона от одного seed дают
идентичные метрики), но окно закономерно меняется от эпохи к эпохе.

### Нормализация входа — отложенный хук `[ОТКРЫТО]`
По докстрингу `features.py` нормализацию признаков (если нужна) делает **Стадия 2**,
а не кэш (кэш хранит сырые `[T, C]` для воспроизводимости). Сейчас слот **пуст** —
модель ест сырые LFCC/logmel (`statpool_mlp` частично компенсирует mean/std-пулингом
по времени). Глобальная/поканальная стандартизация — на фазу экспериментов с
признаками/моделью; помечено, чтобы не потерялось (§9).

### Возобновляемость после падения `[РЕШЕНО]`
Требование: стадия, упавшая на N%, при рестарте продолжает с невыполненного. Механизм **разный** для пакетных стадий и для обучения:

- **Стадия 1 (пакет по файлам) — паттерн «пропустить готовое».**
  - Детерминированный путь выхода на каждый вход (id файла + хэш конфига признаков).
  - Перед обработкой: если выход уже есть → пропустить.
  - **Атомарная запись (критично!):** писать во временный `*.tmp`, затем `os.replace(tmp, final)` (атомарно в пределах одной ФС). Иначе падение *посреди записи* оставит битый файл, ошибочно засчитанный как готовый. Без атомарности проверка «существует → пропустить» небезопасна.
- **Стадия 3 (оценка) — «пропустить готовое», но через шарды** `[РЕШЕНО, v12]`. Буквальный паттерн Стадии 1 здесь не работает: выход у оценки **один файл**, а не файл на пример. Поэтому:
  - скоры пишутся порциями (`eval.shard_rows` строк) в `experiments/<exp>/scores_parts/part_NNNNN.parquet`, той же атомарной записью;
  - при рестарте прочитанные из шардов ключи (`dataset_id`, `utt_id`) исключаются из тестового манифеста **до** создания `Dataset`;
  - в конце шарды склеиваются, к ним приклеиваются метаданные манифеста → `scores.parquet`, папка шардов удаляется;
  - рядом лежит `_state.json` — **отпечаток условий** прогона (веса, эпоха, `feature_hash`, `t_fixed`, окно, селекторы). «Пропустить готовое» безопасно только пока готовое посчитано **тем же**: без отпечатка смена весов при живых шардах молча смешала бы скоры двух разных прогонов в один файл. Не совпал — шарды удаляются с предупреждением, это нормальный сценарий, а не ошибка.
  - *Связь «скор ↔ ключ»* держится на порядке: загрузчик оценки собран с `shuffle=False, drop_last=False`, поэтому i-й скор соответствует i-му примеру `Dataset`, чей ключ лежит в `ds.dataset_ids[i]`/`ds.utt_ids[i]`. Именно поэтому фильтрация манифеста делается **до** конструктора — выравнивание тогда сохраняется само, и id не приходится тащить внутрь батча.
- **Стадия 2 (обучение) — паттерн «чекпойнт».** «Пропустить готовое» неприменимо. *(Реализовано в `train.py`.)*
  - Периодически (каждые `ckpt_every` эпох) сохранять чекпойнт: `state_dict` модели + состояние оптимизатора + эпоха (+ метаданные прогона и `best_eer`).
  - При старте: есть свежий чекпойнт → загрузить и продолжить.
  - Та же атомарная запись (tmp + `os.replace`); держать последние `keep_last` чекпойнтов (ротация), чтобы не остаться с единственным битым. **`keep_last` клампится к ≥ 1** — без чекпойнта нет resume.
  - Лог метрик — в режиме дописывания; при возобновлении **дедуплицировать по эпохе** (строки эпох > эпохи чекпойнта отбрасываются).
  - *Опционально:* для бит-в-бит идентичного возобновления сохранять и состояния ГСЧ (`torch`/`numpy`/`random`). Для *валидного* прогона это не нужно — **не реализовано** намеренно (§9).

### Прочее
- **Воспроизводимость:** фиксировать seed; все параметры запуска (включая `device`, `batch_size`, `num_workers`) — в конфиг-файле (`experiments/<exp>.yaml`), чтобы прогон можно было повторить и приложить к работе.
- **Ноутбуки тонкие:** логика — в `src/viz/`, ноутбук только импортирует, вызывает, сохраняет. Каждый ноутбук обязан проходить **Restart & Run All** сверху вниз без ошибок.
- **Фигуры для печати:** единый стиль через `src/viz/style.py`; линейные графики (loss, DET, ROC) — в **вектор** (PDF/SVG); спектрограммы/тепловые карты — растр с DPI ≥ 300. Экспорт — в `reports/figures/`.

## 8. Доменные заметки (специфика анти-спуфинга)

- **Основная метрика — EER** (Equal Error Rate); в литературе проекта она сквозная. Дополнительно встречается t-DCF — **решено не реализовывать** (§9). *(Общая утилита EER — `src/utils/metrics.py`: ROC-интерполяция точки FPR=FNR; используется val-EER на Стадии 2 и итоговым EER на Стадии 3, чтобы числа были сопоставимы. Сопоставимость обеспечена не только общей формулой, но и общим инференс-проходом `utils/inference.py`: скоры для val и для теста получаются буквально одним кодом.)*
- **Конвенция скора `[РЕШЕНО]`:** больше ⇒ спуф (положительный класс = 1, §6.1). ⚠️ В официальных протоколах ASVspoof CM-скор ориентирован **обратно** (больше ⇒ bonafide): при сравнении с чужими скор-файлами или прогоне через официальные скрипты знак надо инвертировать. Конвенция записана в `eval_metrics.json`, чтобы число нельзя было прочитать наоборот.
- **Доверительные интервалы `[РЕШЕНО, v12]`.** К EER прикладывается перцентильный бутстрэп, **стратифицированный по классу**: подлинные и спуф пересэмплируются независимо с сохранением исходных количеств. Причина — EER определяется парой условных распределений скора, а соотношение классов в тесте есть свойство его дизайна, а не случайная величина; общий ресэмплинг «в кучу» добавил бы к интервалу дисперсию классового баланса, которой в реальности нет. **Что интервал не покрывает** (оговорить в работе): неопределённость из-за конечности обучающей выборки и случайности самого обучения — это разброс *одной обученной модели на данном тесте*, а не разброс метода.
- **Для графика результатов** стандарт — **DET-кривая** (detection error tradeoff), по которой читается EER; плюс матрица ошибок. *(Реализовано: `viz/results.py`, ноутбук 04.)* Оси DET — в нормальных отклонениях (probit): различия в области малых ошибок не сжимаются в угол.
- **Две рабочие точки для матрицы ошибок `[РЕШЕНО]`.** `at_val_threshold` — порог выбран на валидации **до** теста, честная точка. `at_eer_threshold` — порог подобран на самом тесте: иллюстрация того, как распределены ошибки в точке равного риска, но **не** оценка обобщения. Обе пишутся и подписываются, чтобы их нельзя было перепутать в тексте.
- **Разбивка EER по отдельным атакам** ценится комиссией: агрегированная метрика скрывает, на каких атаках метод проседает. В нескольких работах обзора это отмечено как слабость — значит, такая разбивка = лёгкий измеримый вклад. *(Реализована; читать вместе с числом записей на атаку — ноутбук 02: EER атаки на десятках записей шумный и несопоставим с атакой на тысячах.)*
- **Нет общего EER по смеси датасетов `[РЕШЕНО]`.** Метрики считаются по каждому `dataset_id` отдельно. Пул по смеси смешал бы разные домены и разные классовые пропорции в одно неинтерпретируемое число; кросс-датасетный вывод читается сравнением отдельных чисел.
- **Фиксированное окно на тесте — не бесплатная операция.** Оценка берёт `t_fixed` кадров с начала записи, как валидация Стадии 2 (ради сопоставимости, §7). Следствия, которые надо оговорить: у длинных записей часть сигнала модель не видит вовсе; у записей короче `t_fixed` сигнал **повторяется** до нужной длины. Для `for-2seconds` (≈2 с ≈ 200 кадров при `t_fixed=400`) это означает, что модель систематически видит удвоенный сигнал — *оценка, не факт:* вклад в проседание метрики есть, но отделить его от собственно доменного сдвига без абляции нельзя (напр. прогон того же теста с `t_fixed=200`). Гистограмма длительностей с отметкой `t_fixed` — ноутбук 02.
- **Кандидаты признаков из обзора** (контекст, не финальный выбор): ручные кепстральные (LFCC, MFCC, CQCC), мел-спектрограммы под CNN, просодика (F0/энергия/длительность), SSL-эмбеддинги (wav2vec2/HuBERT/WavLM — тяжёлые, на CPU очень медленные).
- **Утечка диктора между сплитами** — известный источник завышенных метрик: если записи одного диктора попадают и в `train`, и в `test`, метод может опознавать диктора, а не подлинность речи. Поэтому при назначении сплита деление **по диктору** предпочтительно (§6.3). Для датасетов без `speaker_id` это ограничение, которое надо **честно оговаривать** в работе.
- **Кросс-датасетная постановка** (учить на одном, тестить на другом) — известная болевая точка: метрики там заметно проседают. Каркас (колонка `dataset_id`, склейка манифестов) поддерживает её бесплатно. *Оценка, не решение:* «оценка переносимости лёгкого метода между датасетами» — потенциально защитимый ракурс новизны; не фиксируется сейчас, но и не закрыт архитектурой.

Канал — **под-ось внутри** условия, а не часть его определения (см. выше про C1–C7): основная разбивка идёт по `condition`, `transmission` её уточняет.

Структура DF-условий читается как готовая ось эксперимента: базовая точка (`nocodec`) → одиночное сжатие трёх кодеков в двух уровнях качества → двойное перекодирование (`mp3m4a`, `oggm4a`). Расшифровка `high`/`low` как уровней битрейта — **чтение имён, не проверенный факт**; конкретные битрейты брать из evaluation plan ASVspoof 2021 и цитировать оттуда.
